- 會改動：`docs/design/pipeline.md` 的「1. Scan」與「2. Compare」，以及它的 `.zh-TW.md`。
- 相關：pipes 草稿（已併入 [architecture](../design/architecture.zh-TW.md#transport) 與 [pipeline](../design/pipeline.zh-TW.md) 後刪除，最後一版在 `e32348a`）的待決定「兩個語意問題」，查過之後發現兩邊的記憶體和最大的目錄成正比，原因在排序；[架構重新設計](architecture-redesign.md#b-線metadata-的並行)的 B2，K 個 lister 同時列目錄。

## 問題

一個目錄的名稱，現在要整個讀進記憶體、排好序，才能往下走。三個地方都用同一個函式 `fsys::read_entries`（`src/fsys.rs`），讀完在記憶體裡排序：

- **Source 的掃描**（`src/scan.rs`）：manifest 裡一個目錄的項目要照名稱遞增送出，所以先排好，再照順序 stat。
- **Destination 的比較**（`src/compare.rs`）：自己的目錄也排好，和 manifest 做 merge；`sync` 時，這份列表要留到這個目錄的最後一段，才找得出 Source 沒有、要刪的項目（`src/destination/receive.rs` 的 `extras`）。
- **刪除整棵樹**（`src/remove.rs`）：其實不需要排序。

每個名稱在記憶體裡約占 60 到 80 bytes：`Vec` 本身、配置的開銷，加上名稱，這是估的，沒有量。100 萬個名稱約 70 MB，1,000 萬個約 700 MB，兩邊各一份，而且沒有上限。decider 不在其中：它每個目錄只記幾個計數（`src/destination/decider.rs` 的 `Open`）。**這句是錯的**，2026-10-29 做第 3 步時發現：decider 留著一個目錄的每一批，等到最後一批，見 [Destination 的 decider](#destination-的-decider)。

## 提案

**超過一個記憶體上限，就在磁碟上排序**，一段一段排，再合併（chunk merge sort）；沒超過的照現在，完全不碰磁碟。2026-10-28 使用者決定。

### 做法

1. 讀目錄時，名稱累積到上限 M，就在記憶體裡排好，寫成一個排好序的段（run）到暫存檔，清空，繼續讀。
2. 讀完，把所有的段做 k 路合併，照順序一個一個交給下游：Source 拿去 stat，Destination 拿去 merge。
3. 交出來的順序和 bytes，和現在在記憶體裡排的一模一樣，所以 manifest 不變，dry run 的輸出也不變。

### 記憶體有保證

- **M = 64 MiB**，每個正在列的目錄一份，算名稱與每個名稱的開銷；約 100 萬個名稱以上才碰到。B2 有 K 個 lister 時，最多 K × 64 MiB。
- **合併時**，每段只要一個讀的 buffer，64 KiB。段太多時，例如超過 128 段，先每 128 段合併成一段、刪掉原本的，再往下合併；同時開著的檔案與 buffer 都有上限，128 × 64 KiB = 8 MiB。
- 這兩個常數，buffer 與一次合併幾段，是實作時的初始值，驗收時量過再調。

### 盡量少用磁碟

- **front coding**：段裡的名稱排好了序，相鄰的常有共同的前綴，只存「和前一個共用幾個 bytes」加上不同的後半，以及名稱的種類。
- **再用 zstd 等級 1 壓**。兩者都便宜。
- 磁碟用量的峰值，約是全部名稱壓縮後的大小；中間那一層合併時，最多再多一組。

### 暫存檔

- **放在 `std::env::temp_dir()`**：有設 `TMPDIR` 就用它，沒有就用 `/tmp`；macOS 上 `TMPDIR` 平常就指向每個使用者在磁碟上的暫存目錄。同 GNU `sort` 做外部排序時的做法；使用者要換位置，設 `TMPDIR` 就好，Ferry 不多一個選項。2026-10-28 使用者決定。
- **`/tmp` 是 tmpfs 時**，例如 Fedora、Arch，Debian 13 起也是預設，段就寫進了記憶體：Ferry 自己的記憶體有上限，整台機器的卻沒省到。要避開，就設 `TMPDIR`。
- **不留垃圾**：暫存檔一建立就沒有名字。Linux 上用 `O_TMPFILE`；不支援的地方，例如 NFS 或 macOS，就以隨機的名字建立，馬上 unlink。檔案只靠開著的 fd 存在，程式怎麼結束，正常結束、被 kill 或當掉，kernel 都會收回，不必清理。

### Destination 的 sync 一起改成串流

排好的列表成了一條串流，和 manifest 的每一段邊讀邊 merge：Destination 有、而 Source 下一個名稱已經超過它的，就是多出來的。不必把整份列表留到最後一段，記憶體一樣有上限。

- 找到的多出來的，一批一批交給刪除，不在記憶體裡攢成一份；「多出來的刪完，才 link」這道閘門照舊，要等這個目錄的最後一段。
- 讀不到的名稱，以及不分大小寫的檔案系統上和它互為別名的項目，照現在的做法；這份名單通常很小。

### 範圍

- **做**：Source 的掃描、Destination 的比較，含 `sync` 的串流。2026-10-28 使用者決定。
- **不做**：刪除整棵樹。它不需要排序，該改成一批一批讀、一批一批刪，另外處理。

## Destination 的 decider

2026-10-29 做第 3 步時發現，草稿原本沒算到；使用者決定先暫停第 3 步，寫進來、定了再做。

### 問題

- **一個目錄的每一批，等到最後一批才處理。** `src/destination/decider.rs` 的 `compared` 把比較好的批次放在 `waiting`，最後一批到了，才：`sync` 先把多出來的交給刪除，再依序處理每一批，宣告子目錄、交給建立的執行緒、去要檔案。理由寫在註解：不分大小寫的檔案系統上，先建的 `A` 會被後面才發現的多出來的 `a` 當成多餘刪掉；`copy` 不刪東西，也照同樣的路走。B1 的補完時（4b0bf7f，2026-10-24）就是這樣。所以一個目錄的全部比較結果都留在記憶體裡，直到最後一批。
- **一個目錄的檔案一次全部去要，每個留著狀態直到送到。** 每個要了、還沒來的檔案，decider 各有一份（`Files::targets`）。Source 的 `BACKLOG`（100,000）讓掃描在目錄之間等，擋不住同一個目錄裡的；Source 那邊也留著這個目錄每個要的檔案的路徑，直到讀完。
- **之前寫錯的**：pipes 草稿說「decider 每一段比較完就要那一段的檔案」，本草稿說「decider 每個目錄只記幾個計數」，pipeline 文件說一批比較完就去要它的檔案（已改正）。都沒有對過程式。

### 量到的

本機 tmpfs，第 2 步的 build（96a4293），每 20 ms 取 `VmHWM`，分開 Source 與 Destination：

| 情境 | Source | Destination |
|---|---|---|
| 一個目錄 100 萬個空檔，首次複製（目的地沒有這個目錄） | 126–127 MiB | 741–786 MiB |
| 同上，dry run | 96 MiB | 167 MiB |
| 1000 個目錄、各 1000 個空檔，首次複製 | 79–84 MiB | 247–266 MiB |
| 一個目錄 100 萬個空檔，已經在、沒有變動，再複製一次 | 108 MiB | 229–233 MiB |
| 同上，dry run | 94 MiB | 196 MiB |

- 首次複製時 Destination 的目錄不存在，沒有列表要排序，所以那 750 MiB 全在 decider；同樣 100 萬個檔案分在小目錄裡，少約 500 MiB。
- 由兩兩相減推的，沒有逐項量：等最後一批的批次，100 萬個項目約 150 到 170 MiB（首次複製的 dry run）；Destination 的列表約 60 到 70 MiB（沒有變動的 dry run 減去首次的 dry run）；100 萬個要了的檔案的狀態，約 500 到 600 MiB（首次複製減去它的 dry run）。
- 所以第 3 步照原本的計畫做完，只省得到增量同步時的列表與子目錄名單；首次複製幾乎省不到。

### 做法

**等最後一批的規則：**

- **(A) 只有 `sync` 而且 Destination 的目錄已經在時才等。** `copy`，或目錄不在（就不會有多出來的），每一批比較完就處理、就去要檔案。首次複製與 `copy` 都不等；`sync` 進一個已經在的大目錄，照舊留著全部的批次。
- **(B) 等著的批次超過上限，就寫到磁碟，**和名稱的段一樣，最後一批到了再讀回來處理。規則不變，記憶體有上限；多寫讀一次，序列化每一批的項目、比較結果與 `present`。
- **(C) 不再等，每一批比較完就處理，連 `sync` 也是；刪多出來的之前，先看它是不是列出時的那一個**（同一個 inode），不是就不刪，所以不會刪掉剛建的別名。要重新驗證不分大小寫的檔案系統上各種別名的情形，例如多出來的是目錄、新建的是同名的檔案。

**要了的檔案：**

- **(D) 要了、還沒寫完的檔案設上限，**例如 10 萬個，同 Source 的 `BACKLOG`：到了就先不要，decider 先不拿新的批次，比較的執行緒等它，manifest 的窗口用完，Source 的掃描就等，回壓一路自然傳回去。要配 (A) 或 (C)：一批一批處理，才能在目錄中途停下；配 (B) 時，留著的批次已在磁碟上。decider 現在從一條佇列拿所有事件，要改成停下拿批次時，照樣拿送到的資料與寫完的回報，否則等不到檔案寫完；要對過[不互相卡死的規則](../design/architecture.zh-TW.md#transport)。
- **(E) 不設限，**接受和一個目錄要的檔案數成正比，寫明。

### 其他和子目錄數成正比的（2026-10-29 盤點）

決定 decider 的做法之後，再對過兩邊的程式，還有兩處沒算到：

- **Source 送 manifest 那邊的 `Expected`**（`src/scan.rs`）：路徑上每個目錄宣告過的子目錄名稱與 ID，等 lister 走到時照順序拿掉，用來說出沒來的目錄 `Unlistable`。
- **decider 的 `Directories::open`**（`src/destination/decider.rs`）：宣告過、還沒收尾的子目錄，各留路徑與完整的項目，收尾時要用。深度優先時，一個目錄的批次都送完才往下走，所以它的子目錄同時都在。
- 量到的：一個目錄 30 萬個空的子目錄，首次複製 Source 119–120 MiB、Destination 340–346 MiB；已經在、沒有變動時，116 與 372 MiB。

2026-10-29 使用者決定這兩處也一起做，用同一套機制：超過上限就寫成磁碟上排好的段；`Expected` 照順序拿，順序讀；`Directories::open` 照名稱查，用分塊索引，和比較時的子目錄名稱共用。

**做 3d 時發現的**（2026-10-29）：

- **decider 不做 I/O**，`Directories::open` 不能照上面說的寫到磁碟、從磁碟查；這一點在決定時沒有算到。一個宣告過、還沒進去的子目錄，在 decider 裡會變的只有「要收尾」（它父目錄的部分建了它或改了它之後）與正在建時的工作數（受「交出去的部分 10 萬個項目」限制），它的項目不會變。
- **Destination 的 manifest 檢查（`Check`，`src/manifest.rs`）也每個子目錄留一筆**：宣告過的目錄照 ID 留著父目錄的 ID 與名稱，到它結束、它宣告的都結束才放掉；盤點沒有列到。還沒開始的目錄只有父目錄 ID 與名稱，ID 照宣告的順序遞增。它在收 manifest 的執行緒裡，不是 decider。
- 估計（照結構大小 `Open` 128 bytes、`Check` 的 `Directory` 80 bytes，加上鍵、路徑與 HashMap 的空間，沒有分開量）：每個子目錄 decider 約 300 bytes、`Check` 約 180 bytes。
- 量到的（本機 tmpfs，一個目錄 30 萬個空的子目錄，首次複製；3c 對做了 `Known` 與 `Expected` 的 build）：Destination 338 對 308 MiB；Source 116 對 128 MiB：`Expected` 沒超過上限時全留在記憶體裡，一筆是兩個 `Vec`，比原本一個 `Vec` 加 ID 大，超過上限才不再長。`sync` 一個已經在、沒有變動的 100 萬檔目錄，Destination 237 對 235 MiB。
- 2026-10-29 使用者決定兩處都限住，先 `Check` 再 decider：`Check` 把還沒開始的目錄照 ID 放進 `Keyed`，開始時照 ID 查；decider 只為進去了或正在建的目錄留 `Open`，還沒進去的只在父目錄上計數，它自己的項目與父目錄那部分有沒有改它，由比較那一邊照名稱留著，在它的第一部分（或 `Unlistable`）一起帶來；建不出來的另外記。

## 其他做法

- **一律在記憶體裡排。** 現在的做法；目錄夠大時，記憶體沒有上限。
- **暫存檔放 `/var/tmp`**（systemd 與 FHS 的慣例，大的暫存檔放這裡，在磁碟上），或先以 `statfs` 看 `temp_dir()` 是不是 tmpfs、是就改用 Ferry 在那台機器上的目錄。都能避開 tmpfs；使用者選了 std，最簡單，也同 GNU `sort`。
- **連 stat 的結果一起寫進段。** 不需要：Source 照排好的順序才 stat，段裡只要名稱與種類。
- **不排序。** manifest 的合併比較靠兩邊同一個順序，不排就要換一套比較的方法。

- [x] **Destination 比較時，開著的目錄的子目錄名稱。**（2026-10-29 做第 3 步時發現）`src/compare.rs` 的 `Frame` 留著目錄裡所有可能是目錄的名稱（`subdirectories`），manifest 往下走到子目錄時，靠它判斷這邊有沒有，沒有就不去開；它也和子目錄數成正比。做法有四：(1) 寫到磁碟，順序讀，子目錄沒照名稱來時直接試著開；(2) 寫到磁碟，分塊壓縮加索引，任何順序都能查；(3) 不記名稱，一律直接試著開，Destination 沒有的子目錄各多一次失敗的系統呼叫，NFS 上各一個往返；(4) 這次不處理。現在的 Source 只有一個 lister，子目錄一定照名稱來，交錯要到 B2 的 K 個 lister 才會有。2026-10-29 使用者決定 (2)：直接做好，任何順序都能查。段的格式因此改成分塊（見計畫第 3 步），Source 的合併與 Destination 的查詢共用一種。
- [x] **和 pipes、B2 的先後。** 2026-10-28 使用者決定：在重排 B2 時一起排。它和 transport 無關，但 Destination 的串流 merge 和 B2 的 page、pipes 的 manifest 記錄都會碰到比較的那一段。同日重排：pipes 做完之後做這份，B2 的平行比較再建在這裡的串流上（[B2](architecture-redesign.md#b-線metadata-的並行)）。

## 計畫

1. **外部排序。** 一個獨立的部分：讀名稱、超過 M 就寫段、front coding 與 zstd、k 路合併、多層合併、沒有名字的暫存檔。測試：以測試用的覆寫把 M 與一次合併的段數設得很小（同現在 `Hello` 裡的 `part_entries`），隨機的名稱，含共同前綴長的、不是 UTF-8 的，結果要和在記憶體裡排的一模一樣；中途結束後，暫存目錄裡沒有留下任何檔案。
   - **做完時定的**（2026-10-29）：
     - 在 `src/sorted.rs`：`Sorter` 收名稱，算到 64 MiB（名稱的 bytes，加上每個名稱的 `Listed` 與配置約 48 bytes）就排好寫成一段；`finish` 時沒寫過段就在記憶體裡排好交出，完全不碰磁碟，寫過段就把各段與手上剩下的一起合併，剩下的那份不另寫成段。`sorted::list` 讀一個目錄、交出排好的名稱；`fsys::list_entries` 是 `read_entries` 拆出來的列目錄，照目錄的順序一個一個交出，`read_entries` 照舊（刪除整棵樹還用它）。
     - **段的格式**：每個名稱是和前一個共用幾個 bytes（varint）、其餘的長度（varint）、其餘的 bytes、種類一個 byte；整段是一條 zstd 等級 1 的串流。
     - **多層合併**：同一層的段滿了一次合併的數量，就合成上一層的一段、放掉原本的；`finish` 時段還太多，先把最低層的那幾段合起來，所以同時開著的段不超過一次合併的數量。
     - **暫存檔**：Linux 上以 `O_TMPFILE` 在 `std::env::temp_dir()` 建立；不支援時（NFS、macOS）以不會和別人重複的名字建立（`O_EXCL`、`O_NOFOLLOW`，0600），馬上 unlink。寫不了或讀不回時是 `TempFailed`，訊息說出暫存目錄，以及可以設 `TMPDIR`；`sorted::is_temp_failure` 讓第 2、3 步認出它，讓傳輸失敗，而不是當成這個目錄列不出。
     - **和草稿不同：一次合併 32 段，不是 128**。量到的：128 段亂數名稱（每段 2 萬個，約 20 bytes 一個）合併時多用 28 MiB，每段約 220 KiB，是 64 KiB 的讀取 buffer 加上 zstd 解壓的狀態與視窗；草稿估的 128 × 64 KiB = 8 MiB 沒算後者。zstd 等級 1 的視窗預設 2^19，合併 128 段要 45 MiB；限在 2^16，壓出來一樣大（每個名稱約 10.4 bytes），所以限住。32 段約 7 MiB，守住草稿說的量；代價是名稱超過 32 段，也就是約 2 GiB，才進入多層合併。
     - 寫完一段後，下一段的 `Vec` 照上一段的筆數先配好，不從空的倍增，免得多占一倍。
     - 測試：隨機的名稱（共用長前綴的、不是 UTF-8 的、各種種類），在記憶體裡、一次合併、一次 3 段的多層合併，結果都和在記憶體裡排的相同；沒有名稱、一個名稱；讀到一半放掉，讀的時候與之後暫存目錄都是空的；以名字建立的暫存檔馬上沒有名字；暫存目錄不存在時是 `TempFailed`，訊息有那個目錄與 `TMPDIR`；一個真的目錄經磁碟排序，和 `read_entries` 相同。

       - 開始過的，以它在父目錄那份裡的編號記成範圍（`Keyed::find`，這步加的，查到時連編號一起給）；子目錄照順序開始時是一段，所以不隨子目錄數長。
       - 寫不了暫存檔時 Destination 失敗，訊息是「keep the directories announced」加上 `TempFailed`；不說成 Source 送了不對的 manifest。
       - 順帶改的：結束時還有目錄沒開始，訊息給它的路徑；原本只給名稱。
       - 測試：原本 `Check` 的每個例子，另外以每筆都寫到磁碟再跑一次，結果相同；一個目錄 300 個項目、200 個是目錄，都寫到磁碟，從最後一個倒著開始，路徑對、每個只能開始一次，還有沒開始的就結束時說出第一個的路徑，都說列不出時可以結束；暫存目錄不在時不是 invalid manifest、有 `TMPDIR`；`Keyed::find` 在磁碟與記憶體裡的編號。
       - 量到的（本機 tmpfs，一個目錄 30 萬個空的子目錄，首次複製，和上一個 build 輪流各 2 次，負載約 4）：Destination 266–272 對 324–344 MiB；Source 不變；時間 6.52–6.79 對 6.41–6.52 秒，次數少，看不出差別。
4. **驗收與文件。** 本機一個目錄 500 萬個空檔：首次複製、增量同步、`sync` 刪掉一半，量兩邊的峰值記憶體與時間，和改之前輪流量；暫存目錄在磁碟上與在 tmpfs 上各一次。改寫 pipeline 的 Scan 與 Compare，中英兩版。
