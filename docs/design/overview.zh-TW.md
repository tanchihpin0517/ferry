# Ferry 設計概觀

## 目標

Ferry 要取代 rsync。它首先必須勝過 rsync 的是速度。

## 術語

| 術語 | 意義 |
|---|---|
| client | 你執行的 `ferry` 指令。它負責準備、啟動一次傳輸的兩個 server、在兩者之間轉送，並顯示它們回報的內容。它的生命週期與指令相同 |
| server | client 透過 transport 在某個 host 或本機上啟動的 `ferry server` 行程。它執行一個 peer，並在其 control connection 關閉時結束 |
| peer | 傳輸的一方，一律在 server 中執行 |
| Source, Destination | 讀取檔案的 peer，以及寫入檔案的 peer |
| record | 資料串流中的一個檔案：標頭、內容與 BLAKE3 雜湊 |
| frame | record 串流中一段 2 MiB 的片段，以 zstd 單獨壓縮。frame 的邊界不理會檔案的邊界 |
| packet | 在 connection 上傳送的單位：`[type][length][payload]`。其類型為 control、manifest、needs、data 或 results；資料壓縮時，manifest 也壓縮，成為它自己的一條 stream。一個 data packet 最多攜帶一個壓縮後 frame 的 64 KiB |

## 已決定

**原則的先後。** 兩條原則衝突時，排在前面的優先：

1. **可靠：** 每個檔案都完整、正確、持久保存；打錯的路徑不會造成損害。
2. **結尾的斜線絕不改變行為：** SOURCE 與 DESTINATION 有沒有結尾的斜線，結果都一樣。
3. **結果與 rsync 相同：** 同樣的輸入，留下同樣的結果與結束狀態。
4. **速度：** 傳輸開始之後的速度。

下面各節分別詳述。

### 先求可靠再求速度

Ferry 先求可靠，再求快速。兩者衝突時，可靠優先。

**一次傳輸所需的一切，都在開始前備妥。** 在 Ferry 掃描、比較或碰觸任何檔案之前，每條 connection 都已開啟並登入，每個 host 上的 server 都已在執行。任何需要你介入的事，例如密碼、OTP，或首次安裝前的詢問，都在一開始就問完，因此已經開始的傳輸絕不會停下來等你，也絕不會因為缺少一條原本可以先開好的 connection 而半途失敗。準備需要多久就花多久：其中沒有任何部分為了省時間而與傳輸重疊。

**速度指的是傳輸開始後的速度。** 從那時起，當速度與其他目標衝突時，速度優先，除非下文某節另有說明。rsync 慢有兩個結構性的原因，Ferry 兩者都會處理：

1. **它只用一個執行緒。** Ferry 讓傳輸的每個 stage 都平行執行。
2. **它一次處理一個檔案。** Ferry 把許多小檔案一起送出，再在接收端拆開。

### rsync 也做的事，結果與 rsync 相同

使用者從 rsync 而來。同樣的 SOURCE、DESTINATION 與選項，Ferry 在 DESTINATION 留下的結果，以及結束狀態，與 `rsync -a SOURCE/ DESTINATION/`（`sync` 則是加上 `--delete`）相同。過程中說些什麼是 Ferry 自己的事：訊息、警告、進度、儀表板與詢問的方式都不在此限。

- **不同之處是決定的，不是碰巧的。** 每一項都列在下表，附上原因，並由測試檢查確實不同。
- **rsync 怎麼做，以實際執行為準，** 不憑記憶。
- **可靠優先：** 拒絕重疊的根目錄、`sync` 到家目錄前先詢問，都是為此而不同。**結尾的斜線絕不改變行為，** rsync 的則會。除此之外，這條原則優先於速度：能更快、卻會留下不同結果的做法，要照上面的方式決定。

`tests/rsync.rs` 在每次 push 時，在同樣的目錄樹上執行兩者，比較每個路徑的種類、內容、權限、mtime、符號連結目標、擁有者與連結數，以及結束狀態（分成 0、23、24 與錯誤）：涵蓋各種項目、各種根目錄對上各種根目錄、一種項目所在之處換成另一種、重跑、刪除、讀不到的東西、掛載點、擁有者與裝置檔。刻意不同之處，它檢查確實不同：

| 情況 | rsync | Ferry | 原因 |
|---|---|---|---|
| SOURCE 結尾沒有斜線 | 把 SOURCE 本身複製進 DESTINATION | 複製其內容，與有斜線時相同 | 常見的錯誤；見下面的「兩個複製內容的指令」 |
| 把檔案複製到尚不存在的 `new/` | 建立目錄 `new`，把檔案複製進去 | 建立檔案 `new` | 結尾的斜線絕不改變行為 |
| root 無法設定的擁有者，例如被 squash 的地方 | 不設定權限與 mtime，檔案停在 `0700`；結束狀態 23 | 拿掉 setuid 與 setgid，其餘照設，並發出警告；結束狀態 0 | 否則檔案在這裡會以 root 的身分執行；其餘照設，就不會每次都重傳 |
| DESTINATION 在 SOURCE 裡面，或反過來 | 把 SOURCE 複製進自己，或刪掉它 | 拒絕 | 打錯的路徑 |
| `sync` 遇到讀不到的目錄之後 | 不再刪除任何東西 | 只保留與讀不到的項目同名的東西，其餘照刪 | 讀取錯誤不是保留其他一切的理由 |
| `sync` 到 `/` 或家目錄 | 照做 | 先詢問；沒有終端機就拒絕 | 打錯的路徑 |
| 還沒開始就被拒絕的傳輸，例如目錄複製到檔案上 | 結束狀態 3 | 結束狀態 1 | Ferry 的 3 是 `ferry update --check` 發現新版 |

### 每個檔案都完整正確並持久保存

接收端最終路徑上的檔案，要嘛是舊版本，要嘛是完整且經過驗證的新版本，即使斷電之後也是如此。這一點與速度衝突時，完整性優先。

1. **以檔案為單位的原子性。** Ferry 把每個檔案寫在看不到的地方，等檔案完整後才給它最終名稱。在 Linux 上，檔案系統支援時，檔案寫入期間沒有名稱（`O_TMPFILE`），完成後以 `linkat` 取得自己的名稱；那個名稱已有東西時，先取得暫存名稱，再重新命名蓋過去。其他情況，例如 macOS 或 NFS，每個檔案寫到同一目錄下的暫存名稱，例如 `.foo.ferry-XXXX`，再重新命名。沒有就地寫入的模式。
   執行中斷或失敗時（例如 Source 失敗或 connection 中斷），Destination 都會刪除它未完成之檔案的暫存檔。沒有名稱的檔案，不論行程怎麼結束，都會跟著消失；只有 Destination 本身當機或被終止，才可能留下暫存名稱，而且只發生在以暫存名稱寫入的情況。
2. **端到端驗證。** 傳送端在讀取每個檔案時以 BLAKE3 計算雜湊，接收端則在寫入時計算雜湊。只有兩個雜湊相符，檔案才會取得它的名稱。檔案最多讀到開啟時的大小，與 rsync 相同；讀取期間變小或讀取失敗的檔案會回報為錯誤，且不會重送。讀取期間有變動的檔案，保留它開啟時的 mtime，因此下一次執行會發現它變了，除非那時它的 mtime 在 `--modify-window` 之內仍算相同：就地改寫、大小不變，而且在預設下與那個 mtime 落在同一秒內的改寫不會被發現，副本保留讀到的內容，新舊混雜，與 rsync 相同。`--modify-window -1` 會比較到奈秒。
3. **預設即持久保存。** 每個檔案在取得名稱前都會 `fsync`。少了這一步，斷電可能使名稱已寫入磁碟，資料卻沒有。為了在大量小檔案時仍負擔得起，Ferry 以批次處理：平行 `fsync` 一批檔案，替整批命名，再對每個目錄 `fsync` 一次。這次執行建立的根目錄，是它所在目錄中的一個新名稱，所以結束時也會對那個目錄 `fsync`。這預設開啟，`--no-fsync` 可將其關閉。

   在 macOS 上，`fsync` 只把資料交給磁碟機，磁碟機仍可能在自己的快取中重新排序，因此在一批檔案的 `fsync` 與重新命名之間，Ferry 對每台磁碟機設一道屏障（`F_BARRIERFSYNC`）：該批的每個檔案都先於它們的任何名稱抵達儲存媒體。傳輸完成時，一次 `F_FULLFSYNC` 會清空磁碟機的快取，因此 Ferry 回報為已複製的內容都已在儲存媒體上。在 Linux 上，`fsync` 本來就會等待儲存媒體，所以兩者都不需要。

Ferry 不讓整個目的地目錄樹具備原子性。中斷的執行可能留下新舊檔案混雜，但每個檔案都是完整的。再執行一次 Ferry，就能讓目的地達到正確的狀態。

### 第一版至少涵蓋 `rsync -a`

`rsync -a` 代表 `-rlptgoD`，Ferry 第一版全部保留：

| rsync | 保留的內容 |
|---|---|
| `-r` | 目錄，遞迴處理，包含空目錄 |
| `-l` | 符號連結，複製為連結而不跟隨 |
| `-p` | 權限位元，包含 setuid、setgid 與 sticky |
| `-t` | mtime，在兩邊檔案系統都允許時精確到奈秒 |
| `-g` | 群組 |
| `-o` | 擁有者 |
| `-D` | 裝置檔、FIFO 與 socket |

中繼資料在檔案取得名稱之前套用，讓新內容與其中繼資料同時出現。擁有者與群組在模式之前設定，因為 `chown` 會清除 setuid 與 setgid。目錄的 mtime 在其中所有內容寫完之後才設定，由最深的目錄開始，因為寫入目錄會改變它的 mtime。

接收端在寫入時，絕不跟隨目的地中已存在的符號連結。每個路徑都以 `openat` 與 `O_NOFOLLOW` 逐一解析各個組成部分，因此目的地中的連結無法把寫入導向目的地之外。擁有者、權限與 mtime 也以同樣的方式設定，絕不經過連結：比較之後被換成符號連結的項目會失敗，而不會讓目的地之外的檔案被改動。硬連結則是另一回事：被換成指向外部檔案的硬連結時，設定的會是那個檔案的屬性，因為硬連結就是那個檔案。在 Linux 上，若 `fs.protected_hardlinks` 開啟（大多數發行版預設如此），無法對不屬於自己的檔案建立硬連結；macOS 沒有這種保護。

若 Ferry 缺少設定某個項目的權限，它會略過該項並發出警告，而 rsync 則默不作聲。例如：非 root 使用者無法把擁有者設為其他使用者、無法設定自己不屬於的群組、無法設定別人擁有的項目的群組、權限或 mtime，也無法建立裝置檔；root 在被 squash 的地方（例如 NFS）無法設定擁有者；FAT 不保存權限。檔案本身仍會傳輸。

### 兩個複製內容的指令 `copy` 與 `sync`

Ferry 有自己的 CLI，而非與 rsync 相容的 CLI，就像 ripgrep 之於 grep。取代 rsync `--delete` 的，是指令的選擇：

| 指令 | 讓 DESTINATION | 等同 rsync |
|---|---|---|
| `ferry copy SOURCE DESTINATION` | 包含 SOURCE 中的一切，並保留它原有的其他內容 | `rsync -a SOURCE/ DESTINATION/` |
| `ferry sync SOURCE DESTINATION` | 與 SOURCE 相同，刪除它原有的其他內容 | `rsync -a --delete SOURCE/ DESTINATION/` |

兩者都把 SOURCE 的內容複製到 DESTINATION 中，就像 SOURCE 以斜線結尾一樣，不論它是否真的如此：從 `data` 到 `backup`，`data/x` 會成為 `backup/x`，絕不會是 `backup/data/x`。rsync 對 `data` 與 `data/` 的區分是常見的錯誤來源，Ferry 沒有這個區分。每個指令只接受一個 SOURCE，因為多個來源的內容會在同一個 DESTINATION 中相互衝突。

### 在 Linux 上以 `getent` 查詢名稱

Linux 的 release 是靜態 musl build，看不到 LDAP 或 SSSD 帳號，因此擁有者與群組透過系統的 `getent` 依名稱對應；見 [Linux 上的靜態 musl build](architecture.zh-TW.md#以-getent-查詢名稱)。

## 提議

### 常見 rsync 用法的對應寫法

常見的 rsync 用法需要有文件記載的對應寫法。若日後發現直接替換的相容性很重要，可以再加上相容層。

### `-a` 中繼資料的行為

- **`-a` 是預設。** Ferry 不需任何旗標就保留上述所有項目。
- **擁有者與群組依名稱對應，與 rsync 相同。** manifest 攜帶數字 ID；在第一個使用某個 ID 的項目之前，Source 會送出它的名稱，僅送一次。Destination 把每個名稱對應到自己的 ID；未知的名稱保留其數字。`--numeric-ids` 不送任何名稱。ID 0 絕不對應。
- **無法設定的不算差異。** 這個行程無法設定的擁有者，以及別人擁有的項目的權限或 mtime。否則每個這樣的項目，每次執行都會看起來有變動。
- **權限警告會彙總。** 沒有 root 時，每個檔案都可能無法保留其擁有者，若每個檔案一則警告，會淹沒其他一切。Ferry 每種情況回報一則警告，附上數量與幾個路徑範例：無法設定的擁有者、權限或 mtime，因無法設定執行時的擁有者而拿掉的 setuid 或 setgid，以及無法建立的 socket 與裝置檔。以 `--verbose` 列出每個路徑仍有待實作。
- **裝置編號照原樣複製。** Linux 與 macOS 對主、次裝置編號的編碼方式不同，因此在兩者之間複製的裝置檔不太可能有意義。

### `ferry sync` 的行為

**已依所述實作。**

- **刪除在傳輸期間執行，一次一個目錄**，與 rsync 的預設相同。Source 列得出、但讀不到的名字仍在 manifest 中，標記為無法讀取，Destination 對同名的項目保持原樣：來源端的讀取錯誤絕不會讓檔案看起來是多餘的。rsync 則在 I/O 錯誤後完全停止刪除，因為它不知道遺失的是哪個名字。中途停止的傳輸可能讓 Destination 比原本少；再執行一次就會補齊。
- **多餘的檔案在傳輸期間逐一目錄找出。** 當 Destination 從 manifest 取得某個目錄的完整清單時，它讀取自己那份目錄，並記下 Source 沒有的項目。並在那時、在建立該目錄的任何東西之前刪除它們，什麼都不保留。
- **`ferry sync --dry-run` 會列出將被刪除的項目**，以及將傳輸的項目，依 manifest 順序。
- **SOURCE 與 DESTINATION 不可重疊。** 每個 server 告訴 client 它的根目錄在 kernel 眼中是什麼：它的 device 與 inode，以及它上面每一層目錄的 device 與 inode。DESTINATION 若就是 SOURCE、在 SOURCE 裡面，或包含 SOURCE，`copy` 與 `sync` 都會在任何改動之前拒絕，dry run 也一樣：把一個目錄 sync 進包含它的目錄，會刪掉它。傳輸期間也做同樣的檢查，所以若有 mount 讓一個根目錄出現在另一個裡面，傳輸會停止：Source 的掃描絕不進入 Destination 的根目錄，Destination 也絕不進入 Source 的根目錄，更不刪除它或它上面的任何目錄。只有兩個 server 在同一個 kernel 上執行時才會比較根目錄；共用網路檔案系統（例如 NFS）的兩台 host，目前不會比較。
- **sync 可能誤清空的 DESTINATION 會先詢問。** `sync` 進 `/`、某個家目錄，或包含家目錄的目錄（例如單獨的 `host:`）時，會先詢問；沒有終端機時拒絕，除非給了 `--allow-dangerous-destination`。`--yes` 不算同意。dry run 只警告。`copy` 不刪除任何東西，所以不會詢問。
- 刪除遵循與寫入相同的符號連結規則：絕不跟隨連結離開目的地。
- **除非加 `-x`，刪除會進入 mount point，與 rsync 相同。** 一個多餘的目錄若是 mount point，或其中有 mount point，會連同另一個檔案系統上的內容一起刪除。加 `-x` 時，不刪除 Destination 根目錄以外的檔案系統上的任何東西，也不刪除這種目錄本身；包含這種目錄的目錄會連同它一起保留，其中其他的東西照常刪除，並發出警告。加 `-x` 時掃描也停在 mount point：送出 mount point 本身，但不送其中的內容，與 rsync 的 `-x` 相同。

### 日後支援並已在設計中預留空間

- 硬連結（rsync `-H`）
- 稀疏檔案（rsync `-S`）
- xattr（rsync `-X`）
- `--verify`：從磁碟重新讀取每個寫入的檔案，以抓出磁碟或檔案系統的錯誤，代價是所有內容都要讀兩次

### 不在計畫中

ACL（rsync `-A`）、atime（`-U`）、建立時間（`-N`）與檔案旗標。POSIX ACL 與 macOS 或 NFSv4 ACL 無法互相對應。

### 範圍僅限單向

Ferry 讓目的地與來源一致。以下不是目標：

- 雙向同步（unison 與 Syncthing 的領域）
- 持續監看檔案的變動
- 整個目的地目錄樹的原子切換
- 續傳部分傳輸的檔案：中斷的檔案會從頭重送。若有需要，可能再重新考慮。
- 差異傳輸：變動的檔案整個送出，如同 rsync 的 `--whole-file`。

## 待解問題
