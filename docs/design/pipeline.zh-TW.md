## 原則

**已決定。** 每個 stage 在其工作允許的範圍內都平行執行，而且沒有逐檔的往返。

**已決定。** 每個 stage 都有自己的工作執行緒池，stage 之間以有界佇列相連。如此一來，最慢的 stage 可以增加工作執行緒，而不必改動其他 stage，有界佇列也會施加背壓，讓記憶體用量保持有界。每個 stage 受限於不同的因素：

| Stage | 受限於 | 平行化的效益 |
|---|---|---|
| 掃描目錄、`stat` | 中繼資料系統呼叫 | 大，尤其在 NFS 與 Lustre 上，但在那裡有上限；見[掃描](#1-掃描) |
| 雜湊 | CPU | 大 |
| 壓縮 | CPU | 大 |
| 在 Destination 上寫入（create、write、chmod、utime） | 中繼資料與磁碟 | 大；小檔案時常是瓶頸 |

目前的實作中，每個 stage 最多有 16 個工作執行緒，或與機器的核心數一樣多，但掃描與比較例外，一個列出時，它們同時最多只向檔案系統要求九件事。在 Linux 上，行程最多只在 8 個核心上執行，除非 `--cpus` 另有指定；只要有一個 NUMA node 的核心夠多，這些核心都在同一個 node 上，因為分散在兩個 node 上時，同樣的複製要多花一半的時間。但各 stage 的工作執行緒數仍依機器的核心數，因為它們大多在等檔案系統。在 96 核心上複製 20 萬個 4 KiB 的檔案，限制在 8 個核心時，ext4 上一樣快或更快，CPU 只用一半或更少；NFS 上一樣快，而工作執行緒也只有 8 個時要多花約一成時間：

| Stage | 工作執行緒 | 順序 |
|---|---|---|
| 掃描 | 一個列出，或 `--listers` 說的個數，各一個目錄，8 個 `stat` | 依交出的順序寫出：一個列出時，就是 manifest 的固定順序 |
| 比較 | 一個列出 Destination 的目錄，或 `--listers` 說的條數 lane，各一個目錄，8 個 `stat`，一個套用 | 依 manifest 的順序，每批比較完就套用 |
| 讀取 | 開啟檔案，2 MiB 以內的整個讀，較大的一次讀 2 MiB 的一段，並計算雜湊 | 任意順序：每個檔案都帶有其 ID |
| 送出 | 一條 data sender 把每個檔案或每一段寫成 data pipe 上的一筆記錄 | 依擁有者交出的順序寫出 |
| 壓縮，在 transport 裡 | 連線壓縮時，8 條壓縮 data 的塊 | 照序號排回 |
| 檢查 | 8 條以雜湊檢查每個檔案或每一段 | 依到達的順序往下交 |
| 寫入 | 每個一個完整的檔案，或大檔的一段 | 任意順序 |

檔案由讀取執行緒讀取：2 MiB 以內就整個讀，否則一次讀 2 MiB 的一段，照順序讀：前一段讀完才讀下一段，由任何一個空著的讀取執行緒讀，系統因此能像讀任何依序讀取的檔案一樣預讀。從旋轉硬碟讀時，16 個讀取執行緒同時讀同一個檔案的段，只有它速度的六成。16 個讀取執行緒不論大小同時讀 16 個檔案，照需要的順序；最多派出 32 個，讓每個讀取執行緒都有下一個在等。16 個 128 MiB 的檔案複製到記憶體，從 NFS 讀時，大檔一個接一個要 3.2 秒，現在 2.0 秒；從旋轉硬碟讀，16.2 秒與 15.4 秒；2 萬個 4 KiB 的檔案和以前一樣快。先需要的先讀，每個檔案由一個讀取執行緒讀：排在小檔前面的大檔多到和讀取執行緒一樣多時，會佔滿所有讀取執行緒，小檔就等；只有一個大檔時，它只佔一個，小檔在旁邊讀。同一個檔案的段一次寫一段、照順序，由任何一個空著的寫入執行緒寫到檔案中的位置。因此沒有檔案會整個放在記憶體中。

各 stage 的執行緒、它們之間的佇列、在哪裡保持順序，以及以綠色標示的 [transport](architecture.zh-TW.md#transport)：

![一次傳輸的工作執行緒、佇列與 transport：在 Source 的 server 上，有讀 answers 的主執行緒、帶 16 個讀取執行緒的擁有者（owner），以及把每個檔案寫成 data pipe 上一筆記錄的 data sender；在 transport 裡，連線壓縮時由 8 條執行緒壓縮的 data 塊，以及每條 stream 一個 pump，還有它的生命線；兩者之間是 client 建好、自己不碰的 1 到 8 條 stream；在 Destination 的 server 上，每條 stream 一個讀取者，data 的塊由 8 條執行緒解壓縮，接著是讀 data 的執行緒、8 個檢查執行緒、feeder、帶 16 個寫入執行緒的決策者、4 個重新命名執行緒、送出 answers 的 pump，以及它的生命線；並標出每個佇列的上限，以及哪些邊保持順序](../assets/pipeline-workers.svg)

每項逐檔或逐塊耗時的工作，即讀取、檢查與寫入，以及 transport 的壓縮與解壓縮，都在執行緒池中執行。重新命名也是，但同一個目錄的檔案同一時間只由一個執行緒改名，因為同一目錄的重新命名會互搶目錄的鎖。其他單一的執行緒負責把工作往下傳。其中兩個，即把每個需要的檔案交出去讀取與送出的 Source 擁有者，以及把每個檔案交給寫入執行緒的 Destination 決策者，是每個檔案都會經過的點。兩者都不做任何 I/O：各自保存自己這一側要做什麼的一切，一次接收一件其他執行緒告訴它的事，再說要做什麼，所以它們做的事能以合成的事件測試；Destination 的決策者也判斷每個錯誤代表什麼。以合成的事件，它處理 20 萬個小檔，從比較到取得名稱，自己的時間是 0.13 秒。peer 寫它們的 [pipe](architecture.zh-TW.md#transport)，由 transport 經 client 在兩個 server 之間建好的 stream 送出，條數照到最遠的 host 的往返時間需要，每 15 ms 一條、最多八條，每條一個 pump：第一條帶每一條 pipe，data 的塊走任一條；另一側每條一個執行緒讀它，從不等 peer，data 的塊照編號排回。沒帶結束就結束的 pipe 算斷，傳輸失敗。它的沉默不會讓它斷：對方在不在，由 [monitor](architecture.zh-TW.md#monitor) 以心跳判斷。每一側有一條生命線 thread，等著 server 的標準錯誤，它的 monitor 一不在了，就讓 server 停下。

**已決定。** 在任一側，任一 stage 失敗，那一側的所有 stage 都立刻停下。它的失敗就是原因，而且只有第一個才是：其他 stage 接著碰到的，例如佇列或串流在它們底下被關掉，都是它的後果，絕不會取代它被回報。原因只告訴另一側一次，也就是唯一的那則 `Error`，`Done` 絕不在它之後。告知之後，不再改動任何東西：每個 stage 在建立、刪除或改變任何東西之前都會檢查，而在佇列上等待的 stage，停止一來就會醒來。另一側告知的失敗同樣是原因，不會回送給它。

**已決定。** 一個錯誤讓它的項目單獨失敗、成為警告，或讓傳輸停止，依錯誤是什麼而定，不論在哪裡遇到：

| 類別 | 例如 | 怎麼處理 |
|---|---|---|
| 項目失敗 | 檔案或目錄打不開、讀不了、列不出、比較不了、寫不進、改不了名或收不了尾；雜湊不符；`EIO` | 遇到時以 answers 的 `Failed` 回報並計數；傳輸繼續，結束狀態為 1 |
| 警告 | 這個行程不能設、或檔案系統不保存的擁有者、權限或 mtime，例如 root 被 squash 時的 `chown`、對應不到 ID 的擁有者、FAT 上的 `chmod`；因擁有者設不了而拿掉的 setuid 或 setgid；列出之後、讀取之前就消失的項目 | 每種一則警告，附數量與幾個路徑，在結束時顯示；項目照樣複製，消失的則略過；不算失敗 |
| 傳輸停止 | 磁碟滿、配額用盡或唯讀（`ENOSPC`、`EDQUOT`、`EROFS`），因為之後的每個項目都會同樣失敗；協定或 manifest 錯誤；connection 或串流失敗；根目錄不能用；內部錯誤 | 第一個原因讓兩側都停止，如上 |

在 Destination 上，遇到錯誤的執行緒，例如建立者、刪除的執行緒、writer、改名的執行緒或收尾的執行緒，不判斷它屬於哪一類，只把錯誤連同設不了的屬性交回；由決策者判斷。

**已決定。** 每個 build 都以 mimalloc 作為全域記憶體配置器，因為每個 stage 都會從許多執行緒同時配置與釋放緩衝區；見 [Linux 上的靜態 musl build](architecture.zh-TW.md#處處都用-mimalloc-作為記憶體配置器)。

## 階段 1 準備

**已決定。** 在讀寫任何檔案之前，client 一步接一步地讓兩個 peer 就緒。每一種執行，無論任一側是本機還是遠端，都經過相同的步驟；對於本機上的一側，[本機 transport](architecture.zh-TW.md#transport) 會讓步驟 2 與 3 成為空步驟。

1. **讀取引數**，檢查位置，並為每一側的位置取得 transport。
2. **開啟 SSH connection**，連到這次執行涉及的每個 host，登入，一個 host 接著一個：每個 host 一條，那裡的一切都走它；見 [Connection](architecture.zh-TW.md#connection)。這是第一件觸及 host 的事，而且由 transport 單獨完成。SSH connection 開啟時不執行任何工作：它只是登入並就緒。密碼或 OTP 在這裡輸入。
3. **探測每個 host，並在缺少時安裝此 build**。直到此時，host 上的工作才開始：client 透過 transport 開啟 host 的第一個 session，也是唯一的一個，它跑一段腳本探測 host，等每個安裝都問過，再在那裡安裝此 build；接著 session 成為 Ferry 在那裡的 [monitor](architecture.zh-TW.md#monitor)，經由不跑 shell 的 channel 替 client 啟動 host 上其餘的一切，`--remote-sudo` 時 sudo 的檢查也在其中；見 [control connection](architecture.zh-TW.md#transport)。每個 host 只探測一次，不論有幾側在那裡；探測同時說明各側在那裡的根目錄是什麼，這決定檔案是否要複製進目錄。所有問題都在安裝任何東西之前問完，而每個 host 都裝好此 build 之後，才啟動任何一個 server：先啟動的 server 要等另一個。
4. **啟動兩個 server**，每一側一個，各自使用自己的一條 control connection，隨它結束：在 host 上，是 monitor 啟動它的那條 channel；在本機，是 client 啟動它時的管道。並在其上**交握**：比對 build，peer 得知各自的角色與選項。
5. **建立傳輸用的 stream**：一對 socket，兩端由 client 交給兩個 server，到 host 上的 server 則走該 host 的 SSH connection。它可能在 server 的 control connection 之前或之後到達。傳輸期間它斷了，傳輸就失敗：不會重建。

- **所有需要詢問你的事都在這裡詢問。** 密碼、OTP 或首次安裝前的詢問，都在傳輸之前；傳輸期間什麼都不問。
- **兩側都不會有任何變更。** 準備期間的失敗或 Ctrl-C，會讓兩邊的目錄樹保持原樣，沒有需要清理的東西。
- **準備不與傳輸重疊。** 即使能節省時間，Source 也不會在 connection 登入期間開始掃描：傳輸只在擁有所需的一切之後才開始。

## 階段 2 傳輸

**已決定。** 每個 peer 都就緒之後，Source 開始掃描，以下的 stage 會持續執行，直到 Destination 完成。每個 stage 的小節，在圖中第二階段都有其編號。

### 1. 掃描

![掃描與比較：在 Source 上，K 個列出執行緒（除非 --listers 另有指定，就是一個）依深度優先列出目錄，相對於父目錄開啟每一個，並把其名稱以每批 256 個交給 8 個 stat 執行緒，結果依序放回，由 manifest 送出者給予 ID，寫上 manifest 的 pipe；manifest 經由 stream 送到 Destination，其比較執行緒（或 K 條 lane）對 manifest 列出的每個目錄列出一次，並與各批合併，8 個 stat 執行緒對兩側都有的項目做 quick check，結論依序放回給決策者，由它安排套用並寫回 answers，根目錄則由讀 manifest 的執行緒套用後告訴它；下方是一棵範例目錄樹、它依序的 manifest 記錄，以及 Destination 如何合併其中一個目錄](../assets/pipeline-scan.svg)

**已決定。**

- **Ferry 有自己的掃描器。** 現有的 crate 都不合適。ripgrep 與 fd 使用的 `ignore` 會逐一回報項目，順序不固定，也沒有表示某個目錄已完整的訊號。`jwalk` 的形態合適，但已不再維護。
- **一個執行緒列出，八個執行緒 stat。** 掃描分為兩部分。列出目錄，也就是開啟它並讀出其名稱，由一個執行緒負責，一次一個目錄，依名稱深度優先。哪些名稱是目錄，也就是接下來要去哪裡，它從列出的結果本身得知，不必等它們的 stat；檔案系統沒有提供這項資訊時，它自己對那些名稱執行 stat。它把每個目錄的名稱交給 8 個執行緒的池，這些執行緒依交付的順序執行 stat，結果也依該順序傳回。因此檔案系統同時最多只會收到一個列出請求與 8 個 stat：在許多人共用的 server 上，例如 NFS，不論目錄樹如何，掃描的負載都有上限。
- **目錄依開啟時的檔案描述子讀取，一次讀很多名稱。** 在 Linux 上，列出執行緒從頭讀它開啟的那個檔案描述子，每次讀取最多容納 256 KiB 的名稱。rustix 的 `Dir` 會為了讀取再開一次目錄，在 NFS 上等於再問一次 server 它有沒有變，而且一次只讀幾個名稱；在 WekaFS 上，每次讀取都是一趟 7 到 10 ms 的往返，最多帶回約 2,500 個名稱。那樣在 WekaFS 上列出一個有 5,000 個項目的目錄要 99 ms，現在是 22 ms；100 個項目的目錄是 1.7 ms，現在是 0.9 ms；在 NFS 上，10 個項目的目錄是 0.40 ms，現在是 0.28 ms。Destination 的比較執行緒也以同樣的方式讀取它的目錄。macOS 仍使用 rustix 的 `Dir`。
- **一個目錄留著的東西有上限，超過就放到磁碟上。** 一個目錄的名稱在記憶體裡排序，最多 64 MiB，連每個名稱的開銷一起算，約一百萬個名稱。超過時，每 64 MiB 排好，寫成暫存檔裡的一段（run），名稱被取用時再合併這些段，一次 128 段，更多時分層合併：名稱出來的順序不變，所以 manifest 也不變。一段以 front coding 存成最多 64 KiB 的塊，每塊各自用 zstd 等級 1 壓縮；記憶體裡只留每塊的位置與第一個名稱，所以合併 128 段只占 7.2 MiB。其他隨一個目錄變大的東西，也都這樣留著，各自同一個上限：Source 上，還要列出的子目錄、送出了還沒列出的子目錄，以及送出了還沒說比較過的項目；Destination 上，它的列表、它的子目錄名稱、`sync` 在它裡面要刪的、`sync` 扣住的批次、檢查為它宣告的子目錄留的，以及決策者要知道的它們的項目，見[比較](#2-比較)。照鍵的順序留著的記錄，照鍵找時只讀一塊，最後讀的那塊留著，所以照順序找時每塊只讀一次。沒超過上限的目錄完全不碰磁碟。暫存檔放在 `TMPDIR`，沒設就是 `/tmp`，與 GNU sort 相同：`/tmp` 是 tmpfs 時，它們一樣在記憶體裡，設 `TMPDIR` 就能移開。每個暫存檔一建立就沒有名稱，所以不論行程怎麼結束，都不留下任何東西；建不出來時，傳輸失敗，並說出在哪裡建、以及由 `TMPDIR` 決定。一個目錄裡 500 萬個空檔：首次複製時 Source 的峰值 146 到 152 MiB、Destination 185 到 190 MiB，改之前的 build 是 550 到 568 MiB 與 2,702 到 2,801 MiB，時間 25.8 到 26.6 秒，原本 29.8 到 30.6 秒；其中 1% 的檔案不同的 sync，160 到 168 MiB 與 226 到 235 MiB，原本 376 到 377 與 806 到 826，時間相同；刪掉一半的 sync，150 到 168 與 307 到 336，原本 248 到 250 與 903 到 1,182，時間相同：暫存檔放在磁碟上或 tmpfs 上都一樣。10 萬個目錄各 10 個檔、1,000 個目錄各 1,000 個檔的樹，複製起來和以前一樣快，或更快。刪除一個目錄連同它的一切時，例如 `sync` 刪掉 Source 沒有的目錄，其中每個目錄也是一次讀一部分；見[比較](#2-比較)。
- **守住上限，讓有很多子目錄的目錄多花時間。** 首次複製一個目錄裡 100 萬個空的子目錄要 23.6 到 24.9 秒，有上限之前是 20.8 到 21.4 秒，Source 196 到 209 MiB，原本 260 到 274 MiB；dry run 22.6 到 23.2 秒，原本 20.9 到 21.3 秒。每個宣告過的目錄都由檢查與扣住批次的那個 stage 記下、序列化，超過上限就壓縮寫到磁碟，進去時再讀回來，比原本的 map 費時：dry run 時，Destination 讀 manifest 的執行緒多跑了 0.65 秒，那個 stage 多 1.08 秒，Source 等 manifest 窗口共 1.33 秒、54 次，原本是 0.02 秒。複製時，決策者對交給建立者的項目設的上限也讓 Source 等：100 萬個目錄在它們的父目錄裡一次建一個，以前是和掃描它們同時進行；拿掉這個上限，複製要 22.0 到 22.7 秒，Destination 則是 554 到 562 MiB，而不是 280 到 317 MiB。
- **曾嘗試更平行地掃描，後來放棄了。** 最多 16 個工作執行緒曾平行地預先讀取目錄，最多一百萬個項目，再由重新排序緩衝區依序送出。在一棵有 134,000 個項目的 NFS 目錄樹上，那樣快了 1.5 到 2 倍，但它在最忙的時候向共用的 server 要求了兩倍的量，而 Destination 也在那裡時，總量還多了 30% 到 50%。在本機磁碟上它反而比較慢，被它的預讀拖住：一千萬個項目的 dry run 花了 9.4 s，只用一個列出執行緒則是 6.6 s。而且為了限制記憶體用量而加入的特例越來越多：因空間不足而放回去的目錄，以及下一個要送出的目錄一定要讀取。只用一個列出執行緒，這些都不需要。
- **`--listers N` 讓兩邊各同時列出 N 個目錄。** 在 Source 上，N 個列出執行緒各一次列一個目錄，從共用的待列目錄中拿下一個：每個列完的目錄，它的子目錄排成一疊，取最上面那個目錄的第一個，所以每個都盡量往下走，大家一起往下。每個邊列邊把它那個目錄的批次交給 stat 執行緒，每批先在它們的 pool 裡占好位子，再取下一個序號；一個目錄的批次全部交出之後，它的子目錄才會被列，所以每個目錄都排在宣告它的那一批之後，什麼都不必扣住。列出執行緒不進去的，它會說：列出時不是目錄的名稱，隨它那一批說；`-x` 時在另一個檔案系統的，走到時說；manifest 送出者對每個送出的目錄，照名稱留著還沒來的子目錄，有上限。每個列出執行緒各有一個目錄留著的東西的上限，所以 N 個最多是 N 倍；為子目錄開著的父目錄，全部合起來 128 個。在 Destination 上，N 條 lane 同時比較 N 個目錄，見[比較](#2-比較)。一個是預設，就是上面的掃描。多個是給網路上的檔案系統裡有很多小目錄的樹，那裡每次列目錄都是一趟往返。在 fatcat 的 NFS 上，負載 21 到 45，一棵形狀同 `/usr` 的樹，20,436 個目錄、197,263 個項目，每次先改動每個目錄讓快取失效，dry run 用 16 個要 6.8 到 22.0 秒，中位數 12.6，四個要 7.9 到 51.6 秒，一個則是 28.7 到 128.3 秒，中位數 40.7；每一輪裡，16 個都比一個快 1.7 到 10 倍。把它同步到同一台上的一份複本，16 個要 24.1 到 72.2 秒，一個 44.9 到 291.4 秒。在 nano4 的 WekaFS 上，在它的 login node 執行，負載 8 到 17，一棵形狀同那裡一個 Python 環境的樹，17,698 個目錄、176,486 個項目，每次同樣先改動：dry run 的中位數，16 個 1.76 秒、四個 1.99 秒，一個 7.42 秒；同步到一份複本，4.76 與 3.60 秒，一個 7.30 秒。一個時和以前一樣快。不適合從硬碟首次複製：那時小檔會從相隔很遠的地方讀，一個小程式從硬碟這樣、16 個同時讀 8 萬個 4 KiB 的檔案，花的時間約是深度優先的五倍。在本機磁碟上反而比較慢，列目錄便宜，交接卻不便宜：在 tmpfs 上，10 萬個目錄各 10 個檔案的 dry run，四個列出執行緒 3.43 到 3.46 秒，一個 3.01 到 3.09 秒。
- **manifest 是記錄，一件事一筆。** 一個目錄是一個 `In`、它的項目（依名稱排序，附帶中繼資料），以及它的 `Listed`；沒有列的目錄，例如列不出的、或 `-x` 時在另一個檔案系統的，改送 `Unlistable`，其中什麼都不刪。擁有者的名稱在第一次用到之前送出，讀不到的路徑遇到時送出；見 [pipe 攜帶什麼](architecture.zh-TW.md#pipe-攜帶什麼)。沒有任何東西隨目錄變大：掃描不論目錄多大，一次 stat 它的 256 個名稱，每一批的記錄立刻寫出，因此大目錄會由所有 stat 執行緒處理，並在各批完成時送出，絕不整個留在記憶體中。
- **manifest 由 transport 壓縮，成為一條串流。** 連線壓縮時，manifest 的 pipe 是一條 zstd 串流，pump 拿走等著的就壓，Destination 讀的一方邊讀邊解：一個目錄單獨壓，沒什麼可壓的，因為大多數目錄都很小；前面的項目就是它的上下文。在 `/usr`、一個 crate registry 的原始碼與一次建置的產物上，一個項目原本 40 到 55 位元組，在串流中是 13 到 21 位元組，少了 2.6 到 3.4 倍；每個目錄各自壓只有 1.5 到 2 倍。要做的事不多的 sync，送的幾乎只有 manifest。壓縮每個項目不到 1 µs：在 tmpfs 上、warm、要求壓縮時，50.5 萬個項目的 dry run 從 0.40 秒變 0.43 秒，這是 Source 自己壓縮時量的。
- **一個列出執行緒時，manifest 有固定的順序：深度優先、依名稱。** 這就是列出執行緒走的順序，因此不需要重新排序，相同的目錄樹總是產生相同的 manifest，這讓測試可以重現，也讓 `--dry-run` 與 `--verbose` 的輸出在不同次執行之間可以比較。多個時，各目錄的批次依列出執行緒交出的順序交錯，接在別的目錄後面的一批前面有一個 `In`，dry run 列出的順序也不固定。被列為目錄、但 stat 時已不再是目錄的名稱，會連同其下的一切被排除。
- **掃描與傳輸重疊。** Source 絕不等掃描完成才開始傳送，不像 3.0 之前的 rsync。先掃描再排序，會讓網路在整個掃描期間閒置，並把整棵目錄樹放在記憶體中。比網路快的掃描，會在 manifest 的窗口（線路上 2 MiB）用完時等待，而不是把它堆在記憶體中。這些 manifest 不會擋住檔案：sender 手上有足夠的檔案要送，也就是 data 的送出 buffer 至少四分之一滿時，資料排在 manifest 之前；低於這個量時，manifest 又改為優先，讓 Destination 在 sender 送完之前找出更多需要的檔案。需要傳的檔案很少的 sync，manifest 仍以全速送出。
- **待送出的檔案太多，或 manifest 的窗口用完時，掃描會等待。** 兩邊都會記著每個需要的檔案，直到它送出為止，而 manifest 可能遠遠跑在資料前面，例如第一次複製時；因此待送出的檔案超過 100,000 個時，掃描會等待。在途、need 還沒送來的項目，是 manifest 窗口裡的，加上 Destination 收下、還沒比較的：等它的 stat 執行緒的，約 80 批，以及 `sync` 進一個 Destination 已有的目錄時，它最後一批之前的各批，超過上限就放到磁碟上。它們沒有別的上限；窗口算的是線路上的 bytes，所以 manifest 壓縮時在途的項目更多，Source 留著的路徑也更多，超過上限就放到磁碟上。送出檔案不需要更多的 manifest，Destination 也邊讀邊做，所以掃描一定會繼續；檔案都送出之後，它就不再等待，傳輸失敗時，掃描立刻停止。窗口取代了「還沒比較的項目」的上限之後，待送出的檔案最多有多少，還沒有再量。寫 manifest 的執行緒每一批都要等 owner 點頭，是兩條執行緒之間的一趟往返，而一個目錄不論空不空就是一批：一個目錄裡 100 萬個空的子目錄的 dry run，它等 owner 等了 21 秒裡的 13.5 秒，owner 九成的時間閒著。
- **只有 manifest 有固定的順序。** 讀取與寫入都平行執行，因此檔案以各自完成的順序傳送與寫入。
- **目錄以相對於其父目錄檔案描述子的方式開啟**，使用 `openat`，而非使用完整路徑。這遵循與寫入相同的規則：不跟隨任何符號連結。它也省下路徑查找，這在 Lustre 等檔案系統上很重要。還有子目錄要列出的目錄，會為它們保持開啟，往下走時每一層一個；超過 128 層之後，子目錄改從根目錄逐層重新開啟，以免很深的目錄樹用光檔案描述子。讀取檔案時也一樣：根目錄只開啟一次，由掃描與 reader 共用，檔案所在的目錄從它出發開啟，最近用過的幾個保持開啟，絕不再經由路徑。
- **掃描失敗時，傳輸會立刻停止**，並附上原因。Destination 在等 manifest 的其餘部分，Source 在等 needs，因此悄悄結束的掃描會讓兩邊永遠等下去。反過來也一樣：傳輸失敗時，掃描立刻停止，不必等整棵目錄樹掃完、送完。manifest 結束之前 connection 就關閉，傳輸同樣失敗，dry run 也一樣：到那時為止列出的，並不是全部。
- **掃描絕不進入 Destination 的根目錄。** client 在一切開始之前，就拒絕互相重疊的根目錄；見[概觀](overview.zh-TW.md#ferry-sync-的行為)。但 mount 仍可能讓 Destination 的根目錄出現在 Source 裡面，所以在同一個 kernel 上，Source 會得知該根目錄的 device 與 inode；掃描遇到這個目錄時，傳輸會停止，而不是一邊寫入一邊讀取它。
- **讀不到的東西會回報，掃描繼續進行。** 列得出、但讀不到 metadata 的名字仍會送出，標記為無法讀取，讓 Destination 對同名的項目保持原樣，`sync` 也絕不會把它當成多餘的。無法列出的目錄送出 `Unlistable`，因此其中也什麼都不刪。Destination 只會在 Source 送出完整清單的目錄裡刪除：Source 沒有送出的目錄，連同它底下的一切，根本不會被比較。

**提議。**

- **每個項目依 manifest 順序取得一個 ID。** answers 以 ID 而非路徑指稱檔案。兩個 peer 不需任何排序，就看到相同的 ID。Source 為了回應 needs 而保留每個項目的路徑，只保留到 Destination 說比較過它為止：一批的需要寫進 answers 之後，Destination 就說 `Compared`，從它的第一個 ID 到最後一個，Source 照順序放掉整批都說過比較過的批次。需要的檔案會帶著自己的路徑，等待送出。因此 Source 保留的只是途中的 manifest，大小受窗口與 Destination 的佇列限制，而不是整棵目錄樹；超過上限就放到磁碟上，由讀 answers 的執行緒，而不是不做 I/O 的 owner，從中找出每個需要的檔案。
- **進度隨掃描計算**，如同 rsync：目前找到的檔案數，以及目前送出的檔案數。掃描通常比傳輸快，因此總數很早就會穩定。由 peer 計數，並把數字回報給 client，由 client 顯示。
- **在有幫助之處使用系統特定的呼叫**，例如 Linux 上的 `statx`，只要求 Ferry 需要的欄位。
- **排除模式日後加入時，可以使用 `ignore` crate 的 glob 比對**，而不使用其走訪器。

### 2. 比較

**已決定。** 比較在 Destination 上執行，如同 rsync。Destination 在 manifest 到達的同時，依相同的順序掃描自己的目錄樹，因此兩者可以一個目錄接一個目錄地邊到邊比，任何一側都不必完整：這是線上的 diff。其執行緒見[掃描](#1-掃描)一節圖中的下半部。

- **Destination 的掃描跟著 manifest 走。** 一個執行緒依 manifest 的順序進入 manifest 列出的每個目錄，相對於其父目錄開啟一次，並列出一次。它不會進入 Source 沒有的任何東西：在這裡不存在、或在這裡是別種東西的目錄，其中的一切都需要傳送，不必檢查。`--listers` 大於一時，它把每個目錄的批次依序交給同樣多條 lane 中手上最少的一條，由 lane 開啟、列出並合併；在 lane 上開啟的目錄，要等它所在的目錄比完在它之前交出的批次。比較結果在交出時依 manifest 的順序占好位置，也依這個順序出來：目錄的第一部分仍然排在父目錄宣告它的那部分之後，這是決策者需要的；Source 只有一個列出執行緒時，不論幾條 lane，dry run 的輸出都一樣。一個慢的目錄會擋住它後面的結果出來，最多 64 個，那些照樣在比。
- **每一批都與列出的結果合併。** 目錄的項目到達時分批比較，一批 256 個，到它的 `Listed` 時可能少一些。兩者都依名稱排序，列表和 Source 的名稱一樣是一條串流，因此可以並排依序讀取。Destination 沒有的項目就需要傳送，不必 stat。它有的項目，則由 8 個執行緒的池依序執行 stat，與 Source 相同。Destination 有而 Source 沒有的名稱，就是 `sync` 要刪除的東西；它在各批到達時找出，等目錄的 `Listed` 到達時就找齊，不必再列出一次，刪除時一次 4,096 個。比較執行緒以 ID 找到每個目錄。
- **manifest 在被採取任何行動之前先檢查。** 無論 Source 因為 bug 或惡意送出什麼，Destination 只會碰到其根目錄底下、Source 列出的名字，每筆記錄一到就檢查：根最先出現，而且只出現一次；每個名字都是單一名字，不是 `.` 或 `..`，也不含 `/` 或 NUL；`In` 只能指向父目錄的項目宣告為目錄、而且還沒結束的目錄；每個宣告過的目錄恰好結束一次，以它的 `Listed`，或它的 `Unlistable`，後者只能在它的任何項目之前；一個目錄的名字嚴格依序出現，編號也依序；`End` 只能在每個目錄都結束之後；mtime 的奈秒少於一秒。目錄可以交錯出現，任何守住這些規則的順序都可以。任何其他情況都會立刻停止傳輸，任一 stage 失敗也一樣。檢查為宣告了、還沒開始的目錄留的，由它所在的目錄照 ID 留著，所以不論一個目錄有多少子目錄，都不會多占。在這之下，每個會改變或進入某個名字所指之物的呼叫，都拒絕不是單一名字的東西，路徑也絕不經由 `.` 或 `..` 前進：即使檢查有所遺漏，也到不了所給目錄之外。這兩者每晚都以出錯的 Source 可能送出的東西做 fuzz，manifest 與 data 的記錄一起、任意順序，而根目錄旁的東西都不能改變；兩側讀取的 packet、data 的記錄，以及 pipe 的 frame（壓縮或不壓縮）也一樣，見 `fuzz/`。
- **`sync` 進去的目錄整個一起套用，先處理多餘的項目。** Destination 已有這個目錄時，各批到達時就比較，但在目錄的最後一批比較完之前，不建立任何東西；之後先刪除目錄多出的項目，再依序套用各批，與 rsync 相同：它的檔案可以先寫成沒有名稱的檔案，但要到之後才取得名稱。因此為某個目錄建立的東西，絕不會被當成多餘的，即使檔案系統把兩個名字當成同一個，例如不分大小寫的檔案系統；而以這種另一個名字存在、其實是 Source 讀不到的那個項目，會被保留。Source 自己的兩個名稱若被檔案系統當成同一個，例如 `A` 與 `a`，絕不會兩個都寫入：先建立的那個保有這個名稱，另一個失敗，並說明它被當成了哪個名稱，它底下的一切也一起失敗，因為不會為它覆寫、刪除或寫進任何東西。只有比較時沒有列出的名稱，而且在發現已被占用時，才做這項檢查，所以其他時候傳輸不必為此付出任何代價。目錄的各批由比較的一個 stage 留到那時，超過上限就放到磁碟上。`copy`，或 Destination 沒有的目錄，沒有多餘的項目，每一批比較完就套用。決策者依序接手比較結果，一出來就接手，把一批要改的東西，也就是要建立的目錄、symlink、特殊檔與要設定的屬性，交給最多 16 個建立者，每個各負責一個目錄，因為在同一個目錄裡，kernel 一次只建立一個名稱；它交出去後就接著做下一批，讀取 manifest 的執行緒只負責讀取與分派，只有根目錄由它在任何一批到達之前先套用。只有 dry run 才需要的 stat，也就是會取代目錄的項目、以及實際執行時會保留的多餘項目，由 stat 執行緒做。決策者接手一批時，就去要它的檔案，前提是比較時找到了它的目錄，這一批做完後才取得名稱。要了還沒送到的檔案有 10 萬個，或交給建立者的各批共有 10 萬個項目時，它不再接手新的一批：比較等它，掃描等 manifest 的窗口。首次複製一個目錄裡 100 萬個空檔，Destination 的峰值 174 到 188 MiB；一個目錄的檔案一次全部去要時是 710 到 759 MiB，時間也多一成。一個還沒建立的目錄，它的各批要等父目錄那一批把它建好，它的檔案在它建好時才要求；到那時才說它 `Compared`，讓 Source 可以忘掉已送出的項目。一個目錄要等它自己的 `Listed` 或 `Unlistable` 到達，它的各批，以及父目錄裡建立或修改它的那一批都做完，才算完成。決策者要等一個目錄的第一批或它的 `Unlistable` 到達，或父目錄那一批要建立它時，才留著它：在那之前，它只是父目錄要等的一個，父目錄那一批為它宣告的，也就是它的項目、以及那一批有沒有改它，跟著它的第一批一起來，在那之前由扣住批次的那個 stage 按它所在的目錄留著。首次複製一個目錄裡 100 萬個空的子目錄，Destination 的峰值 281 到 298 MiB，決策者留著每個宣告過的目錄時是 647 到 661 MiB，時間相同。首次複製 20,200 個空目錄，只用一條執行緒建立時 NFS 要 6.5 秒，現在是 2.0 秒；WekaFS 上兩版交錯量，現在不到原本的五分之一。
- **刪除的對象，就是列出的那個目錄。** 比較時，每個目錄相對於其父目錄只開啟一次，其多出的項目就從那同一個目錄、經由它的 file descriptor 刪除，絕不再經由路徑；根目錄底下的其他一切，也都從比較時開啟一次的根目錄出發。途中改指向另一個目錄的路徑，例如被切換的符號連結，或被掛載覆蓋的磁碟，絕不會讓在某個目錄列出的多餘項目，在另一個目錄中被刪除。
- **刪除分散到各個目錄。** `sync` 時，一個目錄多出的項目由最多 16 條執行緒刪除，刪除線自己也算在內，每條各清空一個目錄：在同一個目錄裡，kernel 每刪一個名稱都要取得那個目錄的鎖；在網路上的檔案系統，每個名稱都是一趟往返。列出的結果說不是目錄的，直接 unlink，只有目錄才打開，所以一個檔案只要一趟往返，不是兩趟。一個目錄一次讀 256 KiB 的名稱，照目錄給的順序，每次讀到的刪完才讀下一次：讀到目錄時就把它們排進佇列，下一次讀排在它們下面，所以等著進入的，每個正在清空的目錄最多一次讀的量，同一個目錄也一次只有一個刪除者在刪。清空之後發現不是空的，例如檔案系統在刪除的同時讀目錄時漏了名稱，就從頭再讀一遍，只要前一遍讀到了名稱。刪除一個有 200 萬個空檔與 20 萬個各有一個檔的目錄的目錄，Destination 的峰值 142 到 164 MiB，每個目錄整個讀進來時是 394 到 396 MiB，時間相同；只有那 200 萬個檔時，78 到 86 MiB，原本 286 到 298 MiB。刪除在一條專門的線上進行，一次處理一個目錄的多餘項目，決策者同時繼續往下做：只有那個目錄的各批要等它，因為多餘的項目刪掉之前，那個目錄裡不建立、也不命名任何東西。在檔案寫成沒有名稱的地方，例如 Linux 自己的檔案系統，它的檔案立刻要求，同時寫入；在檔案得以暫存名稱寫入的地方，例如 NFS 與 macOS，它的檔案在之後才要求，因為在同一個目錄裡建立與刪除名稱，只是輪流拿目錄的鎖。一次 sync 要在同一個目錄刪掉 2 萬個檔案、又複製 2 萬個新檔案進去，到 ext4 原本要 0.62 秒，現在是 0.52 秒；在 NFS 上，檔案在刪除的同時寫入時要 19.3 秒，現在和以前一樣是 17.0 秒。一次 sync 要在一個目錄刪掉 2 萬個檔案、在另一個目錄複製 2 萬個新檔案，套用比較結果的執行緒等刪除時，WekaFS 上要 24.6 秒、NFS 上 10.1 秒，現在是 13.5 秒與 7.9 秒，差不多就是刪除本身的時間。刪除 500 個目錄裡的 5 萬個檔案，WekaFS 上原本要 44 秒、NFS 上 8.5 秒，現在是 2.3 秒與 1.7 秒；一個目錄裡的 2 萬個檔案，NFS 上原本要 5.8 秒，現在是 3.5 秒；一個目錄裡的 1 萬個檔案，WekaFS 上原本要 8.7 秒，現在是 6.7 秒。
- **絕不進入、也絕不刪除 Source 的根目錄。** 在同一個 kernel 上，Destination 會得知 Source 根目錄及其上每一層目錄的 device 與 inode。比較時不會進入就是 Source 根目錄的目錄，任何刪除也不會移除其中任何一個，不論在多深的地方：遇到時都會停止傳輸。否則，讓一個根目錄出現在另一個裡面的 mount，會讓 Destination 刪掉 Source。
- **Quick check。** 大小與 mtime 相同的檔案會略過，如同 rsync 的 quick check。mtime 預設以整秒比較，與 rsync 相同，以免時間精度較粗的檔案系統與工具讓未變動的檔案看起來有變動；`--modify-window` 可以放寬這個時間窗，或收窄到奈秒。有變動或不存在的檔案就是一項 need，Destination 寫回 answers，一個檔案一筆記錄。
- **它的成本。** 對已存在的目錄，是一次列出，加上對兩側都有的每個項目執行一次 stat。相較於對 manifest 列出的每個項目都執行 stat，`copy` 多讀一次目錄，`sync` 則少讀一次；它省下 Destination 缺少的每個項目的一次失敗 stat，而在列出時會一併帶回每個項目屬性的 NFS 上，也可能讓 stat 更便宜。空的目的地比較起來沒有任何成本。目錄列出的結果隨各批到達邊讀邊用，有上限。

唯一的往返在 manifest 與 needs 之間，而且是管線化的：Source 在後面的檔案仍在比較時，就開始傳送最先需要的檔案。

**沒有選的做法**（2026-10-28 與 29 日，目錄的上限）。

- **一律在記憶體裡排序**，如同以前：記憶體沒有上限，一個 500 萬個項目的目錄讓 Destination 用到 2,702 到 2,801 MiB。
- **暫存檔放在 `/var/tmp`**，systemd 與 FHS 放大型暫存檔的地方，在磁碟上；或以 `statfs` 看 `temp_dir()` 是不是 tmpfs，是就改用另一個目錄。兩者都讓暫存檔不占記憶體；照 GNU sort 用 `TMPDIR` 比較簡單。
- **把 stat 的結果也寫進段裡。** Source 照排好的順序 stat 名稱，所以段裡只要名稱與種類。
- **不排序。** 邊收 manifest 邊比較，需要兩邊同一個順序。
- **還要列出的子目錄留在記憶體裡**，寫明掃描留的隨它們的數量長：每個約 70 bytes，500 萬個約 350 MB。
- **每一批到了就套用，`sync` 也是**，刪除每個多餘的項目之前，先確認它就是列出時的那一個、同一個 inode，這樣剛建的名稱絕不會被當成多餘的。這得重新檢查每一種兩個名字被當成同一個的情形，其中包括一個多餘的目錄，與以它另一個名字建立的檔案。
- **要了的檔案不設上限。** 一個目錄的檔案一次全部去要、每個留著直到送到，100 萬個約 500 到 600 MiB，這是一次複製與它的 dry run 相減推出來的。
- **檢查用一份記下全部宣告過的目錄。** 記下的只能變多，開始過的就會和還沒開始的一起留著，整次傳輸的每個目錄，先在記憶體裡到上限，再到磁碟上。
- **清空目錄時每次都從頭讀**，這樣就不必靠檔案系統在刪除的同時記住讀到哪裡。在 ext4 上，每次讀都要走過之前清空的區塊，在 NFS 上還要再抓一次，所以讀幾次就把目錄讀過幾遍。

**提議。**

- **`--checksum`，日後再做。** 以 BLAKE3 雜湊而非大小與 mtime 比較檔案，用於必須確認內容相同的情況。它會讀取兩側的每個檔案，因此絕不會是預設。
- **rsync 的其他比較選項等有需要時再做：** `--size-only`、`--update`、`--ignore-existing`、`--existing` 與 `--ignore-times`。

**已決定。** Destination 打不開或列不出的目錄、stat 失敗的項目，都單獨失敗：其中每個項目都回報為失敗並保持原樣，打不開的目錄只說一次，其餘照常比較與複製。這個行程不能設定的，也不算差異：別人的權限、群組或 mtime。

### 3. 讀取與雜湊

**已決定。** Source 讀取每個需要的檔案，最多讀到開啟時的大小，並在讀取時平行地以 BLAKE3 計算雜湊；大於 2 MiB 的檔案一次讀一段、照順序讀，不論大小同時讀 16 個；見[概觀](overview.zh-TW.md#每個檔案都完整且正確)中的完整性規則。由一條執行緒，即擁有者，持有 Source 對要送什麼所知道的一切：已送出還沒比較的項目、需要但還沒讀的檔案、正分段讀取的檔案、交給 data sender 的記錄，以及掃描可以走多遠。它不做 I/O：掃描、讀取執行緒、data sender 與 connection 執行它說的事，再把做了什麼依發生的順序放進同一個佇列告訴它。掃描要等擁有者說可以，才寫出 manifest 的一批；擁有者在那之前就記下這一批的項目，讓 Destination 需要的項目一定在。Source 只開啟仍是一般檔案的東西，而且開啟絕不會等待：掃描後被換成 FIFO、裝置或目錄的檔案，不讀就關掉，並回報為無法讀取。開啟前不先檢查，因為這種檔案極少，而每個檔案多一次 `stat`，在網路檔案系統上就是多一次往返。在 Linux 上，核心允許時以 `O_NOATIME` 開啟，讀取不會更新檔案的存取時間。

### 4. 序列化與壓縮

**已決定。** Source 傳送的資料是 data pipe 上的記錄，一件事一筆；見 [pipe 攜帶什麼](architecture.zh-TW.md#pipe-攜帶什麼)：

- **2 MiB 以內的檔案整個送**，它的位元組與它的 BLAKE3，是一個 `File`；沒讀完整的，帶著原因而不是雜湊。
- **較大的檔案分段送**，每段是從 2 MiB 的倍數開始的 2 MiB，或是檔案在那裡剩下的部分，是一個 `Segment`，帶著它在整個檔案的 BLAKE3 中那一部分的 chaining value。
- **檔案的雜湊與一次讀完整個檔案算出的相同。** BLAKE3 是樹狀的雜湊，對齊、長度為 2 的冪的一段就是其中一棵子樹。Source 讀完所有段之後，以各段的 chaining value 合併出檔案的雜湊，在最後一段之後寫成一個 `Hash`；Destination 每段一到就檢查，檔案取得名稱之前，再檢查由各段合併出的雜湊。
- **需要卻打不開的檔案**是一個 `Unopened`，讓它的目錄不必等它就能收尾。
- **data 以自己的記錄 `End` 結束**，在 pipe 的結束之前。沒帶它就結束的 data pipe，例如失敗的 Source 的，算是被切斷，由決策者說 data 提早結束；Source 的失敗在它的 pipe 結束之前已在 control 上說了，那才是原因。
- **由一條 data sender 寫出**，照擁有者交出的順序，每筆編碼時把檔案的位元組複製一次；同時在等的合成一次寫入，最多 64 KiB，更大的單獨寫。每個小檔各寫一次時，本機 5 萬個 4 KiB 的檔案慢了一成。
- **擁有者最多交給 data sender 16 筆還沒寫出的記錄**：窗口全放在那裡時，本機複製大檔慢了一成，緩衝區的 page fault 多了一倍；這是 16 個 block 等壓縮執行緒時量的。
- **沒有 pack。** 小檔一個接一個，一個檔案一筆記錄；transport 不管記錄的邊界，把 data 切成 2 MiB 的塊，所以相鄰的檔案一起壓縮。
- **2 MiB，與之前的 block 一樣。** 以 crate 的原始碼、建置產物、`/usr`、原始碼的 tar，以及模型權重、數值資料與 zip 的大檔量，每個 block 各自壓縮：2 MiB 的 pack 與 segment，送出的位元組與之前一條檔案串流的 2 MiB frame 相同。8 MiB 時，zstd 1 少送 0.2 到 1.1%，zstd 3 少送 1.5 到 9%；但在 tmpfs 上本機複製一個 4 GiB 的檔案要 3.3 秒，2 MiB 時是 2.9 秒。段是 Source 讀大檔、算雜湊的單位；塊是 transport 壓縮的單位。
- **有變動的檔案整個送出。** 沒有差異傳輸；見[概觀](overview.zh-TW.md#範圍僅限單向)。
- **流量控制是 data pipe 的窗口，加上 Destination 持有的上限。** data 的窗口，線路上 64 MiB，在 Destination 讀的一方讀走時歸還；讀出來、還沒放掉（寫完或失敗）的，另以同樣的 64 MiB 限制，每個檔案至少算 4 KiB。用完時讀的一方就等，窗口不還，Source 就等。所以 Destination 絕不會因為沒有空間而停止讀取 connection：它的 manifest 與其他 pipe 不會卡在資料後面。
- **Destination 可能持有兩倍的 data 窗口。** pipe 之前，額度限的是已送出、還沒寫完的全部；現在窗口限 pipe 裡的，同樣的量再限讀出來的，所以寫得比資料來得慢的 Destination，最多持有 128 MiB。在 nano4 寫到 WekaFS，Destination 的峰值 210 到 230 MiB，pipe 之前 106 到 128；`--data-credit` 設成 16 MiB 時 115 到 131，之前 80 到 86。其中約 20 MiB 不隨額度變，還沒查出是什麼。
- **Source 的每一層緩衝都會填滿。** Destination 較慢時，讀的工作最多 32 個（大檔 64 MiB）、交給 data sender 的 16 筆（32 MiB），以及 data 的送出 buffer 16 MiB（記錄的位元組寫進去時再複製一次），都會滿：最多約 112 MiB。在 nano4 上，Source 的峰值 94 到 100 MiB，pipe 之前 43 到 90 MiB，不論額度。

D16 只考慮速度，讓大檔維持一條長的 record。2026-10-23 為了其餘的理由決定改用 block：大檔不再擋住後面的檔案，而且 block 能單獨重送，這是續傳會需要的；見[架構重新設計](../drafts/architecture-redesign.md)。重送在 2026-10-25 隨重連一起拿掉，block 在 2026-10-29 拿掉：順序由 data pipe 保證，壓縮由 transport 做。留下來的是段，以及每個檔案一筆記錄。

#### 壓縮

**已決定。**

- **transport 壓縮，peer 不壓。** 每條連線的 pipe 壓不壓，由 client 為它決定：連到 host 的以 zstd 等級 1 壓，本機的不壓。`--compress-level <n>` 給每條連線一個等級，本機的也是；`--no-compress` 關閉壓縮，適用於 CPU 比位元組更重要的快速區域網路。
- **data 的塊各自壓縮，平行進行**，由 8 條執行緒負責，像 pigz 那樣：送出 buffer 裡攢滿 2 MiB 就切一塊，或者線路會閒著時，有多少切多少，壓好的加上正在壓的最多 8 塊，在 pump 前面。另一側由 8 條執行緒解壓縮，照序號排回，解好、還沒讀的最多 16 MiB，只有輪到的那一塊例外。
- **壓不小的塊原樣送出。** 已壓縮的檔案（`.gz`、`.mp4`、`.zst`）不會耗費兩次 CPU。
- **其他每條 pipe 是一條 zstd 串流**：manifest、answers、reports 與 control，各自在它的 pump 拿走等著的時壓縮，最多 64 KiB，壓完立刻 flush。線路忙時，bytes 在送出 buffer 裡攢著，壓得更好；不忙時立刻送出，什麼都不等。
- **解壓縮速度幾乎不受等級影響**，因此較高的等級對 Destination 幾乎沒有成本。
- 經 SSH 到 fatcat、等級 1，一個 crate registry 的原始碼（522.5 MiB）在線路上 89.9 MB，以 block 各自壓縮時是 97.2 到 98.6 MB：省 84%，之前 82%。花了 2.4 到 2.6 秒，之前 3.9 到 4.1 秒。
- **在本機，壓縮讓 transport 慢約五分之一。** 本機加 `--compress-level 1` 時，只看 transport，最好的幾次比不壓的慢約五分之一：每塊多複製一次，並在執行緒之間交接。
- **在慢速連線上，短的傳輸比攢起來送得多。** 要等 pump 後面的緩衝區，socket、SSH 的 channel window 與 TCP 的，都塞滿之後，bytes 才會攢起來。連線比壓縮後產生的還慢、傳輸又短時，bytes 改在那些地方排隊，壓成一小段一小段：模擬 100 KB/s 時，dry run 的 53,362 條路徑要 4.06 秒，整條一起壓約 3.35 秒；10 MB/s 時就沒有差別。多花的時間只有一次，最多約 2 MiB 除以速率。

**已決定。** 等級 1，固定不變。最先嘗試的是會自動調整的等級，在送往 connection 的 data packet 佇列一直滿著時便提高。結果太慢：在單一機器上，或磁碟比壓縮執行緒慢時，無論等級多少，佇列都一直是滿的，因此等級一路攀升，直到壓縮成為瓶頸。固定等級 1 或 3 時，在單一機器上複製 1 GiB 的大檔案只要 1.4 s，相較之下為 4.5 到 17 s；透過一條 SSH connection 傳送則為 32 s，相較之下為 42 到 56 s。

### 5. 解碼

**已決定。** Destination 讀 data 的執行緒照順序讀記錄。每個檔案或每一段，在它可以持有時交給 8 個檢查執行緒，以雜湊檢查它的位元組，或以 chaining value 檢查一段的位元組；feeder 依到達的順序，把它們交給決策者。分段檔案的雜湊、Source 打不開的檔案，由讀的執行緒自己告訴決策者；data 結束時，再說有幾筆檔案的記錄，決策者等到那麼多筆。解不開的記錄、或 Source 不會寫的記錄，讓 Destination 當場失敗。讀的執行緒之後，沒有東西會等空間：它持有的有上限，所以比網路慢的磁碟，會以 data 的窗口擋住 Source，而不是塞滿記憶體，或擋住 connection。

**每筆記錄單獨交出。** 每個檔案單獨交給檢查執行緒，再單獨交給決策者，之前則是一個 block 裝好幾個小檔一次交。一個 crate registry 的原始碼（36,240 個大小不一的檔案），在本機複製時，client 與兩個 server 共用 `--cpus` 給的 8 顆核心，幾乎都在忙：檢查執行緒用了 0.75 秒 CPU，之前 0.40 秒，醒來 16,700 次，之前 9,100 次，整次複製比 pipe 之前慢 7% 到 15%；給 24 顆核心時就不慢。

### 6. 寫入

**已決定。** 每個檔案在 Linux 上檔案系統支援時寫成沒有名稱的檔案，否則寫入暫存名稱；驗證其雜湊、套用其中繼資料，再以批次給它名稱。不做任何 `fsync`。暫存名稱的檔案套用中繼資料後就關閉，關閉失敗就讓它失敗，與 rsync 的檢查相同：NFS 上，寫回時的錯誤是在關檔時回報的。這些規則在[概觀](overview.zh-TW.md#每個檔案都完整且正確)中。

**已決定。** 寫入平行進行，每個寫入執行緒一個完整的檔案或一段，同一個檔案同一時間只由一個寫入執行緒寫。以 segment 傳送的檔案，在第一段到達時建立，每一段以 `pwrite` 寫到檔案中的位置，一次一段、照到達的順序：好幾個寫入執行緒寫同一個檔案，只是輪流拿它的鎖；在 WekaFS 上，16 條只有一條速度的六成。從記憶體複製一個 4 GiB 的檔案到 ext4，兩種做法都是 3.1 秒；2 GiB 的檔案到 NFS 都是 3.6 秒。所有段都寫完、而且由它們的 chaining value 合併出的雜湊與 Source 的相同時，才設定屬性。與 Source 讀到的不同，或 Source 沒能讀完整的檔案，就失敗，為它建立的東西都不留下。失敗的檔案以 answers 的 `Failed` 告訴 Source。寫入執行緒每個最多兩件工作，一件在做、一件備著，由決策者交給它們，並回報每件的結果。

**已決定。** 檔案以每批最多 256 個重新命名，由 4 個在整個傳輸期間都存在的改名執行緒負責：決策者在一批滿了時交給它們，或一批的第一個檔案進來 1 秒後還沒滿也照樣交出，就繼續往下做；這樣在沒有更多檔案進來時寫好的檔案，例如大檔還在傳時，那時就取得名稱，不必等到結束。從記憶體複製 2 萬個 4 KiB 的檔案與一個 4 GiB 的檔案到 ext4，最後一個小檔在 1.8 到 2.0 秒取得名稱，原本要等到結束，3.6 秒。其中一個改名這一批裡檔案最多的那個目錄，其他的改名其餘的目錄，一個執行緒一個目錄。同一個目錄的檔案同一時間只由一個改名執行緒負責：kernel 在同一個目錄裡一次只改名一個，靠的是目錄的鎖，所以共用一個目錄的改名執行緒只會互搶這把鎖。只在一個目錄裡的一批，由一個改名執行緒改名；跨好幾個目錄、而且每次改名都要等 server 的一批，由好幾個同時改名。在 WekaFS 上 2 萬個 4 KiB、每個目錄 100 個的檔案，這比一個改名執行緒快 26%；在 ext4 上 20 萬個、寫成沒有名稱的檔案時，快 20%；每個目錄 1,000 個時，兩者都一樣快。除了正在填的一批，最多有兩批等著改名；一個檔案的結果在它改名之後才送出。沒有名稱的檔案，若比較時目錄裡沒有這個名稱，以一次 `linkat` 取得自己的名稱；否則，或者之後有東西佔了這個名稱，就先 link 到暫存名稱，再重新命名蓋過去。等待批次的檔案占著它所在目錄的檔案描述子，同一個目錄的檔案都共用它，為了在收到訊號時刪除它而做的登記也是；沒有名稱的檔案還占著自己的描述子，所以可同時開啟的檔案數較少時，批次只有一半大。每個目錄從根目錄出發、一次一個名字地開啟一次，不經由路徑；最近用過的幾個保持開啟。有暫存名稱的檔案，設好屬性就關閉。可同時開啟的檔案數較少時，批次跟著縮小，不會有檔案因為缺少描述子而失敗。目錄的多餘項目還在刪除時寫好的檔案，要等它那一段做完才取得名稱：這樣等著的檔案，最多到批次之外剩下的描述子允許的數量，至多 65,536 個，等著時不再交工作給寫入執行緒。改名執行緒改完名就放掉檔案，只回報結果。

### 7. 結果

**已決定。** 單一檔案失敗不會中止傳輸。Destination 一發現某個項目無法使其一致，就立即回報，client 則把它顯示給使用者。掃描的結果視為一份 snapshot，不會重送任何檔案；rsync 則會重做一次。每筆檔案的記錄都帶有 Source 開啟該檔案時看到的大小與 mtime，內容最多讀到那個大小，與 rsync 相同：讀取期間多出來的部分不送，下一次執行會發現它的 mtime 改變了。讀取期間變小或讀取失敗的檔案，一個位元組都不送，只送原因，它就失敗；以 segment 傳送的檔案，有一段這樣說之後，其餘都不再送。無法開啟的檔案，包括已不是一般檔案的，由 Source 回報，什麼都不送；Source 也告知 Destination，讓它所在的目錄不必等它就能收尾。

### 8. 收尾

**已決定。** Destination 在一個目錄裡、以及它底下都不會再建立任何東西時，就立刻收尾，設定它的擁有者、權限與 mtime：也就是它自己的 `Listed` 或 `Unlistable` 已經到了、它裡面的每個檔案都寫完了、它裡面的每個目錄也都收尾了。目錄以 ID 找到，它的 `Listed` 或 `Unlistable` 到了就算結束，不論 manifest 接著到哪裡；`Unlistable` 比父目錄的 `Listed` 先到的目錄（掃描從不這樣寫，但檢查放行），要到最後才收尾。最多 16 條執行緒收尾，每條各收一個目錄，由決策者依完成的順序交給它們，也就是由最深的開始；一個目錄要等它底下的目錄都收完尾才收尾，因此之後無法再進入的目錄，要等它底下都沒有東西要建立或收尾時才收尾；決策者在最後一個目錄收完尾後才結束。首次複製 20,200 個空目錄，只用一條執行緒時，ext4（那時每個目錄都要 fsync）要 3.5 秒、NFS 13.2 秒、WekaFS 71 秒，現在是 1.1、6.8 與 49 秒，這是建立目錄也分散到多條執行緒之前的數字；見[第 2 節](#2-比較)。Source 無法開啟的需要檔案，在 Source 告知時就算處理完畢，如同沒能完整讀取的檔案在它送達時那樣：它的目錄不必等它。只有連這樣的告知都沒有、檔案始終沒來的目錄，才在最後收尾，而那個檔案以「從未送來」失敗。Destination 已有、屬於自己、但無法讀取、寫入或進入的目錄，會在掃描開啟它時，先替擁有者補上這三種權限，如同 rsync 的做法，好在裡面作業；要刪除的多餘目錄也一樣，先補上再刪除。這樣的目錄不論裡面是否有變動都會收尾，讓它最後的權限和 Source 一致。Destination 停止之後，不再收任何目錄的尾；若傳輸在它收尾之前就失敗，或多餘的目錄最後沒能刪除，它會設回原本的權限。因此 Destination 對目錄保留的資料，只有已宣告但還沒結束的目錄，以及還有檔案要寫的目錄。若是 `ferry sync`，Source 沒有的項目已經在每個目錄比較完時逐一刪除了。最後，它向 client 回報摘要。

**已決定。** 收不了尾的目錄單獨失敗，以它的項目回報，其他目錄照常收尾。它的擁有者、權限與 mtime 都各自嘗試，不論前一步結果如何；這個行程不能設定的，與檔案一樣是警告。
