## 原則

**已決定。** 每個 stage 在其工作允許的範圍內都平行執行，而且沒有逐檔的往返。

**已決定。** 每個 stage 都有自己的工作執行緒池，stage 之間以有界佇列相連。如此一來，最慢的 stage 可以增加工作執行緒，而不必改動其他 stage，有界佇列也會施加背壓，讓記憶體用量保持有界。每個 stage 受限於不同的因素：

| Stage | 受限於 | 平行化的效益 |
|---|---|---|
| 掃描目錄、`stat` | 中繼資料系統呼叫 | 大，尤其在 NFS 與 Lustre 上，但在那裡有上限；見[掃描](#1-掃描) |
| 雜湊 | CPU | 大 |
| 壓縮 | CPU | 大 |
| 在 Destination 上寫入（create、write、chmod、utime） | 中繼資料與磁碟 | 大；小檔案時常是瓶頸 |

目前的實作中，每個 stage 最多有 16 個工作執行緒，或與核心數一樣多，但掃描與比較例外，它們同時最多只向檔案系統要求九件事：

| Stage | 工作執行緒 | 順序 |
|---|---|---|
| 掃描 | 一個列出，8 個 `stat` | 依 manifest 的固定順序送出 |
| 比較 | 一個列出 Destination 的目錄，8 個 `stat` | 依 manifest 的順序套用 |
| 讀取 | 預先開啟檔案，並整個讀入小檔案（最多 1 MiB） | 任意順序：每個 record 都帶有其 ID |
| 壓縮 | 壓縮 frame | 依串流的順序送出 |
| 解壓縮 | 解壓縮 frame | 依序交給 parser |
| 寫入 | 每個一個檔案；檔案的位元組在剖析時就送達其寫入執行緒 | 任意順序 |

大檔案由傳送端依序讀取，並由一個寫入執行緒依序寫入，因此絕不會整個放在記憶體中。

各 stage 的執行緒、它們之間的佇列、在哪裡保持順序，以及以綠色標示的 [transport](architecture.zh-TW.md#transport)：

![一次傳輸的工作執行緒、佇列與 transport：在 Source 的 server 上，有主執行緒、帶 16 個讀取執行緒的 sender、8 個壓縮執行緒、frame sender 與 pump，其下是 transport 的佇列與 path 端點；中間是在兩個 server 之間轉送的 client；在 Destination 的 server 上，有 transport 的 path 端點與佇列，接著是主執行緒、pump、8 個解壓縮執行緒、frame feeder、帶 16 個寫入執行緒的 parser，以及 8 個重新命名執行緒；並標出每個佇列的上限，以及哪些邊保持順序](../assets/pipeline-workers.svg)

每項逐檔或逐 frame 耗時的工作，即讀取、壓縮、解壓縮、寫入與重新命名，都在執行緒池中執行。單一的執行緒負責把工作往下傳。其中兩個，即寫出 record 串流的 Source sender，以及讀取該串流的 Destination parser，是每個檔案都會依序經過的點。每個 pump 把訊息送進 transport 的 connection，client 把它們轉送給另一個 server，另一側的主執行緒再完整且依序地接收它們；它們走了哪些 path，這些 path 全都平等，是 transport 的事。

### 記憶體配置器

**已決定。** 每個 build 都以 mimalloc 作為全域記憶體配置器，因為每個 stage 都會從許多執行緒同時配置與釋放緩衝區；見 [Linux 上的靜態 musl build](architecture.zh-TW.md#處處都用-mimalloc-作為記憶體配置器)。

## 階段 1 準備

**已決定。** 在讀寫任何檔案之前，client 一步接一步地讓兩個 peer 就緒。每一種執行，無論任一側是本機還是遠端，都經過相同的步驟；對於本機上的一側，[本機 transport](architecture.zh-TW.md#transport) 會讓步驟 2 與 3 成為空步驟。

1. **讀取引數**，檢查位置，並為每一側的位置取得 transport。
2. **開啟每條 SSH connection**，連到這次執行涉及的每個 host，每一條都登入，一次一條；見 [Connection](architecture.zh-TW.md#connection)。這是第一件觸及 host 的事，而且由 transport 單獨完成。SSH connection 開啟時不執行任何工作：它只是登入並就緒。密碼或 OTP 在這裡輸入。
3. **探測每個 host，並在缺少時安裝此 build**。直到此時，host 上的工作才開始：client 透過 transport 開啟 [control connection](architecture.zh-TW.md#transport)，每一條通往它在 host 上需要的程式，用來探測與安裝，並在首次安裝前詢問。
4. **啟動兩個 server**，每一側一個，各自使用自己的一條 control connection，生命週期與之相同，並在其上**交握**：比對 build，peer 得知各自的角色與選項。
5. **開啟傳輸用的 connection**：每個 transport 的 path 加入其 server，client 對每個 server 各持有一條 connection，在它們之間轉送。

- **所有需要詢問你的事都在這裡詢問。** 密碼、OTP 或首次安裝前的詢問，都在傳輸之前，絕不在傳輸期間。
- **兩側都不會有任何變更。** 準備期間的失敗或 Ctrl-C，會讓兩邊的目錄樹保持原樣，沒有需要清理的東西。
- **準備不與傳輸重疊。** 即使能節省時間，Source 也不會在 connection 登入期間開始掃描：傳輸只在擁有所需的一切之後才開始。

## 階段 2 傳輸

**已決定。** 每個 peer 都就緒之後，Source 開始掃描，以下的 stage 會持續執行，直到 Destination 完成。每個 stage 的小節，在圖中第二階段都有其編號。

### 1. 掃描

![掃描與比較：在 Source 上，一個列出執行緒依深度優先列出目錄，相對於父目錄開啟每一個，並把其名稱以每段最多 10,000 個交給 8 個 stat 執行緒，結果依序放回，由 manifest 送出者給予 ID，再排入 pump；client 把 manifest 轉送給 Destination，其比較執行緒對 manifest 列出的每個目錄列出一次，並與各段合併，8 個 stat 執行緒對兩側都有的項目做 quick check，結論依序放回給主執行緒，由它送回 needs；下方是一棵範例目錄樹、它依序的 manifest，以及 Destination 如何合併其中一個目錄](../assets/pipeline-scan.svg)

**已決定。**

- **Ferry 有自己的掃描器。** 現有的 crate 都不合適。ripgrep 與 fd 使用的 `ignore` 會逐一回報項目，順序不固定，也沒有表示某個目錄已完整的訊號。`jwalk` 的形態合適，但已不再維護。
- **一個執行緒列出，八個執行緒 stat。** 掃描分為兩部分。列出目錄，也就是開啟它並讀出其名稱，由一個執行緒負責，一次一個目錄，依名稱深度優先。哪些名稱是目錄，也就是接下來要去哪裡，它從列出的結果本身得知，不必等它們的 stat；檔案系統沒有提供這項資訊時，它自己對那些名稱執行 stat。它把每個目錄的名稱交給 8 個執行緒的池，這些執行緒依交付的順序執行 stat，結果也依該順序傳回。因此檔案系統同時最多只會收到一個列出請求與 8 個 stat：在許多人共用的 server 上，例如 NFS，不論目錄樹如何，掃描的負載都有上限。
- **曾嘗試更平行地掃描，後來放棄了。** 最多 16 個工作執行緒曾平行地預先讀取目錄，最多一百萬個項目，再由重新排序緩衝區依序送出。在一棵有 134,000 個項目的 NFS 目錄樹上，那樣快了 1.5 到 2 倍，但它在最忙的時候向共用的 server 要求了兩倍的量，而 Destination 也在那裡時，總量還多了 30% 到 50%。在本機磁碟上它反而比較慢，被它的預讀拖住：一千萬個項目的 dry run 花了 9.4 s，只用一個列出執行緒則是 6.6 s。而且為了限制記憶體用量而加入的特例越來越多：因空間不足而放回去的目錄，以及下一個要送出的目錄一定要讀取。只用一個列出執行緒，這些都不需要。
- **manifest 的單位是目錄。** 目錄的項目依名稱排序送出，附帶中繼資料：一次送出，或者對超過 10,000 個項目的目錄，分成每段最多 10,000 個、一段接一段送出，讓沒有任何訊息隨目錄變大。每一段作為一份工作執行 stat，因此大目錄會由所有 stat 執行緒處理，並在各段完成時送出，絕不整個留在記憶體中。
- **manifest 有固定的順序：深度優先、依名稱。** 這就是列出執行緒走的順序，因此不需要重新排序，相同的目錄樹總是產生相同的 manifest，這讓測試可以重現，也讓 `--dry-run` 與 `--verbose` 的輸出在不同次執行之間可以比較。被列為目錄、但 stat 時已不再是目錄的名稱，會連同其下的一切被排除。
- **掃描與傳輸重疊。** Source 絕不等掃描完成才開始傳送，不像 3.0 之前的 rsync。先掃描再排序，會讓網路在整個掃描期間閒置，並把整棵目錄樹放在記憶體中。比網路快的掃描，會在有 8 MiB 的 manifest 等待送出時等待，而不是把它堆在記憶體中。這些 manifest 不會擋住檔案：sender 手上有足夠的檔案要送，也就是資料佇列至少四分之一滿時，資料排在 manifest 之前；低於這個量時，manifest 又改為優先，讓 Destination 在 sender 送完之前找出更多需要的檔案。需要傳的檔案很少的 sync，manifest 仍以全速送出。
- **只有 manifest 有固定的順序。** 讀取與寫入都平行執行，因此檔案以各自完成的順序傳送與寫入。
- **目錄以相對於其父目錄檔案描述子的方式開啟**，使用 `openat`，而非使用完整路徑。這遵循與寫入相同的規則：不跟隨任何符號連結。它也省下路徑查找，這在 Lustre 等檔案系統上很重要。
- **掃描失敗時，傳輸會立刻停止**，並附上原因。Destination 在等 manifest 的其餘部分，Source 在等 needs，因此悄悄結束的掃描會讓兩邊永遠等下去。
- **讀不到的東西會回報，掃描繼續進行。** 列得出、但讀不到 metadata 的名字仍會送出，標記為無法讀取，讓 Destination 對同名的項目保持原樣，`sync` 也絕不會把它當成多餘的。無法列出的目錄，依它在父目錄中的樣子送出，裡面沒有任何東西，因此其中也什麼都不刪。Destination 只會在 Source 送出完整清單的目錄裡刪除：Source 沒有送出的目錄，連同它底下的一切，根本不會被比較。

**提議。**

- **每個項目依 manifest 順序取得一個 ID。** needs 與 results 以 ID 而非路徑指稱檔案。兩個 peer 不需任何排序，就看到相同的 ID。
- **進度隨掃描計算**，如同 rsync：目前找到的檔案數，以及目前送出的檔案數。掃描通常比傳輸快，因此總數很早就會穩定。由 peer 計數，並把數字回報給 client，由 client 顯示。
- **在有幫助之處使用系統特定的呼叫**，例如 Linux 上的 `statx`，只要求 Ferry 需要的欄位。
- **排除模式日後加入時，可以使用 `ignore` crate 的 glob 比對**，而不使用其走訪器。

### 2. 比較

**已決定。** 比較在 Destination 上執行，如同 rsync。Destination 在 manifest 到達的同時，依相同的順序掃描自己的目錄樹，因此兩者可以一個目錄接一個目錄地邊到邊比，任何一側都不必完整：這是線上的 diff。其執行緒見[掃描](#1-掃描)一節圖中的下半部。

- **Destination 的掃描跟著 manifest 走。** 一個執行緒依 manifest 的順序進入 manifest 列出的每個目錄，相對於其父目錄開啟一次，並列出一次。它不會進入 Source 沒有的任何東西：在這裡不存在、或在這裡是別種東西的目錄，其中的一切都需要傳送，不必檢查。
- **每一段都與列出的結果合併。** 兩者都依名稱排序，因此可以並排依序讀取。Destination 沒有的項目就需要傳送，不必 stat。它有的項目，則由 8 個執行緒的池依序執行 stat，與 Source 相同。Destination 有而 Source 沒有的名稱，就是 `sync` 要刪除的東西；它在各段到達時找出，等目錄的最後一段到達時就找齊，不必再列出一次。
- **Quick check。** 大小與 mtime 相同的檔案會略過，如同 rsync 的 quick check。mtime 預設以整秒比較，與 rsync 相同，以免時間精度較粗的檔案系統與工具讓未變動的檔案看起來有變動；`--modify-window` 可以放寬這個時間窗，或收窄到奈秒。有變動或不存在的檔案就是一項 need，Destination 會以 needs packet 串流回傳。
- **它的成本。** 對已存在的目錄，是一次列出，加上對兩側都有的每個項目執行一次 stat。相較於對 manifest 列出的每個項目都執行 stat，`copy` 多讀一次目錄，`sync` 則少讀一次；它省下 Destination 缺少的每個項目的一次失敗 stat，而在列出時會一併帶回每個項目屬性的 NFS 上，也可能讓 stat 更便宜。空的目的地比較起來沒有任何成本。目錄列出的結果會保留到它的最後一段到達：一百萬個項目的目錄約 75 MB。

唯一的往返在 manifest 與 needs 之間，而且是管線化的：Source 在後面的檔案仍在比較時，就開始傳送最先需要的檔案。

**提議。**

- **`--checksum`，日後再做。** 以 BLAKE3 雜湊而非大小與 mtime 比較檔案，用於必須確認內容相同的情況。它會讀取兩側的每個檔案，因此絕不會是預設。
- **rsync 的其他比較選項等有需要時再做：** `--size-only`、`--update`、`--ignore-existing`、`--existing` 與 `--ignore-times`。

### 3. 讀取與雜湊

**提議。** Source 讀取每個需要的檔案，最多讀到開啟時的大小，並在讀取時平行地以 BLAKE3 計算雜湊；見[概觀](overview.zh-TW.md#每個檔案都完整正確並持久保存)中的完整性規則。

### 4. 序列化與壓縮

**提議。** Source 傳送的資料，是一條連續的檔案 record 串流，類似 tar：

```text
[header: path, metadata, size][content][BLAKE3][header][content][BLAKE3]...
```

- **小檔案自然地合併。** 一個 record 接著下一個，沒有打包規則，也沒有填充。
- **大檔案是一個很長的 record。** 由一個寫入執行緒依序寫入，而循序寫入很快。
- **有變動的檔案整個送出。** 沒有差異傳輸；見[概觀](overview.zh-TW.md#範圍僅限單向)。
- **流量控制來自 transport。** TCP 與 SSH 在兩個 peer 之間施加背壓。

#### 壓縮

**已決定。**

- **串流以 2 MiB 的 frame 平行壓縮。** frame 的邊界不理會檔案的邊界。超過約 1 MiB 之後，更大的 frame 幾乎無法改善壓縮率，而記憶體用量隨 frame 大小 × 傳輸中的 frame 數增長。大小是固定的；有一個隱藏選項可為基準測試變更它。
- **串流一閒置就送出 frame**，而不只是在 frame 滿的時候。否則一次執行的最後幾個檔案，以及進度，都會等待一個永遠填不滿的 frame。
- **zstd 等級固定，預設為 1。** `--compress-level <n>` 可設定其他等級。解壓縮速度幾乎不受等級影響，因此較高的等級對 Destination 幾乎沒有成本。
- **無法壓縮的 frame 原樣送出。** 已壓縮的檔案（`.gz`、`.mp4`、`.zst`）不會耗費兩次 CPU。
- **`--no-compress`** 關閉壓縮，適用於 CPU 比位元組更重要的快速區域網路。

**已決定。** 等級 1，固定不變。最先嘗試的是會自動調整的等級，在送往 connection 的 data packet 佇列一直滿著時便提高。結果太慢：在單一機器上，或磁碟比壓縮執行緒慢時，無論等級多少，佇列都一直是滿的，因此等級一路攀升，直到壓縮成為瓶頸。固定等級 1 或 3 時，在單一機器上複製 1 GiB 的大檔案只要 1.4 s，相較之下為 4.5 到 17 s；透過一條 SSH connection 傳送則為 32 s，相較之下為 42 到 56 s。

### 5. 解壓縮與剖析

**提議。** Destination 平行解壓縮 frame，再把它們排回原本的順序。接著依序剖析 record。剖析只讀取標頭並把資料往下傳，因此一個執行緒就夠了，而跨越兩個 frame 的檔案也不是特例。

### 6. 寫入

**已決定。** 每個檔案寫入暫存名稱、驗證其雜湊、套用其中繼資料、以批次 `fsync`，再重新命名就位。這些規則在[概觀](overview.zh-TW.md#每個檔案都完整正確並持久保存)中。

**提議。** 寫入平行進行，每個寫入執行緒一個檔案。每個檔案的結果以 results packet 回傳給 Source。

### 7. 結果

**已決定。** 單一檔案失敗不會中止傳輸。Destination 一發現某個項目無法使其一致，就立即回報，client 則把它顯示給使用者。掃描的結果視為一份 snapshot，不會重送任何檔案；rsync 則會重做一次。每個 record 都帶有 Source 開啟該檔案時看到的大小與 mtime，內容最多讀到那個大小，與 rsync 相同：讀取期間多出來的部分不送，下一次執行會發現它的 mtime 改變了。讀取期間變小或讀取失敗的檔案，會補到那個大小以維持串流同步，並標記為未讀完；Destination 丟棄它，它就失敗。

### 8. 收尾

**提議。** 每個檔案都寫完之後，Destination 設定目錄的 mtime，從最深的目錄開始。若是 `ferry sync`，Source 沒有的項目已經在每個目錄比較完時逐一刪除了。最後，它向 client 回報摘要。
