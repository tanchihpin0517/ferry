# 未來的改進

[English](future.md)

Ferry 以後可能做得更好的地方。這裡沒有一項已經排定或決定：哪一項要做時，先在 [docs/drafts/](../drafts/README.zh-TW.md) 寫草稿，在那裡決定。[概觀](overview.zh-TW.md#範圍僅限單向)說不做的，在那之前照舊。

## 跨次執行的大檔續傳

如同 rsync 的 `--partial`：傳到一半的大檔，下一次從斷掉的地方接著傳，而不是從頭再送。

- **為什麼。** 每個 host 只有一條 SSH 連線，斷了傳輸就失敗；重跑時，已經完成的檔案會跳過，但傳到一半的大檔要整個再送一次。檔案越大、連線越不穩，代價越高。
- **可以接在哪裡。** 大於一段的檔案，是一段一段送的，每段到了就對它的雜湊檢查，檔案的雜湊由各段的串起來；所以已經寫好、檢查過的段是知道的。
- **要先決定的。**
  - 寫到一半的檔案要不要有名稱，讓下一次找得到：檔案系統允許時，它在完成之前沒有名稱，否則用暫存名稱，失敗時刪掉。
  - 多大的檔案才續傳，而不是重送。
  - 已經寫好的段，串起來的雜湊要不要從磁碟讀回來重算一次才相信，還是照記下來的用。

## sparse 檔案

如同 rsync 的 `-S`：檔案裡的洞照樣是洞，而不是寫成零。整段都是洞的，就以洞送出，不帶任何 bytes；Destination 留出位置，不寫入。

## 大檔的粗粒度 delta

一個大檔只改了幾處時，只送改了的段：Destination 送出它那份檔案各段的雜湊，Source 對相同的段回「沿用」。比 rsync 的 rolling checksum 粗，只找得到留在原處的段；代價是 Destination 要讀一遍它那份來算雜湊，而不是收整個檔案。

## hardlink

如同 rsync 的 `-H`：在 Source 上是同一個檔案的幾個名稱，在 Destination 上也是同一個檔案，而不是幾份複本。

## 依檔案系統，同一個大檔同時讀幾段

大檔是一段一段照順序讀的，不論大小同時讀 16 個檔案：從硬碟同時讀一個檔案的好幾段，預讀就失效，16 條 thread 同時讀只有一條的六成。每次讀都要等 server 的地方正好相反：

- NFS 上（fatcat，NFSv4.1，`nconnect=8`），同一個檔案的 2 MiB 段由 1、4、16 條 thread 同時讀，691–793、881–1,104、1,065–1,077 MB/s；這樣讀，複製 4 GiB 的檔案到記憶體要 3.74–3.99 秒，照順序讀要 6.30–6.62 秒。
- WekaFS 上，4 條 7.3–9.6 GB/s，一條 3.9–4.0，16 條只有 0.8–1.0；Ferry 自己在那裡約 0.7 GB/s，限制在別處。

Source 會以 `statfs` 查一次根所在的檔案系統，在認得的檔案系統上同一個檔案最多同時讀那麼多段：NFS 8 段，WekaFS 4 段（它的 magic 是 `0x18031977`，`stat` 叫不出名稱），其他一段，和現在一樣。要維護一份檔案系統的清單與上限；根底下掛載的檔案系統會被當成和根一樣；上限定錯了比一段還慢。還沒量：旁邊的小檔因此少了多少，以及其他網路檔案系統。

## WekaFS 上的單一大檔

在 tmpfs 上，4 GiB 的檔案複製要 1.6 到 2.0 秒。在 WekaFS 上，一條 thread 冷讀就有 3.9 到 4.0 GB/s，複製到記憶體卻要 6 秒左右；這是 2026-10-25 stream 層縮薄之前量的，之後沒有再量，原因也沒有追。

## 排在前面的大檔，不讓小檔等

需要的檔案照 need 來的順序讀，同時 16 個，data 的窗口先到先得；先來的大檔佔住 reader。在 fatcat 的 NFS 上，16 個 128 MiB 的檔案排在 2 萬個 4 KiB 的檔案之前，整棵樹 2.37 秒，大檔一次一個時要 3.45 秒，但小檔一半寫好由 0.5 秒變 2.2 秒。有小檔在等時，大檔最多佔一半的 reader。多一條規則，大檔晚一點；在硬碟上，兩者之間來回更多。同時讀 16 個之後，WekaFS 上沒有量。

## 小檔成批交給 writer

決策者把每個小檔當成一件工作交給 writer，writer 寫完一個說一次。tmpfs 上 20 萬個 4 KiB 的檔案，決策者在 1.5 到 1.7 秒裡忙 0.82 秒，writer 約五分之一的時間在忙：現在不是瓶頸。一件工作最多裝例如 16 個檔案或 1 MiB，只拿已經來的，不為了湊滿而等，結果一起回來，各檔案的成敗分開算。決策者多一些要做、要測的；一個檔案的結果要等同一批的其他檔案。

## 多個 lister 時，Source 照路徑的順序讀

`--listers` 大於一時，需要的檔案來自好幾個分支，照來的順序讀；從硬碟讀時，一個小程式輪流從 16 個子樹讀 8 萬個 4 KiB 的檔案要 105.7 秒，深度優先是 21.7 秒。Source 的 owner 會照路徑的順序取等著讀的檔案，像電梯一樣，讓同一個分支的接連讀，也不會有檔案一直等；首次複製時等著的最多 10 萬個，夠排。還沒量：共用一個堆疊的 lister 實際交錯到什麼程度，以及能快多少。

## 峰值記憶體回到 pipes 之前

Destination 讀走時就還 data 的窗口，讀了、還沒寫的另外限在 data 額度之內，所以寫得比資料來得慢時，最多持有兩倍額度，pipes 之前是一倍：寫到 nano4 的 WekaFS，210 到 230 MiB，之前是 106 到 128。Source 讀的工作、記錄與送出 buffer 最多約 112 MiB。做法，可以合用：窗口與持有的各為額度的一半，32 MiB 的窗口在 1 GbE 上到 250 ms 的往返就會限住速度；只縮持有的；Source 的送出者按 bytes 算，交給 transport 的是它的 buffer 而不是複本；或照現在，寫明。另外，窗口與額度依鏈路決定，而不是固定。Destination 約 20 MiB 不隨額度變，還沒找出是什麼。

## 控制訊息不排在資料後面等

SSH 連線上的資料受 data 的窗口（64 MiB）與每條 channel 的窗口限制；同一條 TCP 上之後才寫的心跳、「停」、host 的回報，都排在它後面。在模擬的 250 ms、掉包 1% 的鏈路上，速率約 0.1 MB/s，心跳過去的中位數 6.2 秒、最慢 9.2 秒，Ctrl-C 的「停」到 host 也要這麼久。Destination 會每讀約 256 KiB 說一次讀到哪裡，Source 的 pump 讓已寫出、還沒說讀到的，不超過速率乘以最小的往返再加 1 秒，最少 256 KiB：控制訊息最多晚約一秒加一個往返。pump 多一個等待與它的狀態，速率估計晃動時可能拖慢傳輸，每秒多幾百則小訊息；乾淨的鏈路是不是一樣快，還沒量。

## 慢速鏈路上，pipe 攢一下再送

transport 拿到 pipe 裡的東西就壓，不等更多；鏈路比壓縮後產生的還慢時，bytes 排在 socket、SSH 的窗口與 TCP 的 buffer 裡，而不是在 pipe 裡攢，壓得也少：在模擬的 100 KB/s 上，列出 53,362 條路徑的 dry run 4.06 秒，攢著時約 3.35 秒，首次複製的 manifest 與 data 8.66 秒對約 6.5 秒；10 MB/s 時一樣。傳輸夠長，那些 buffer 滿了就會自己攢。每條 pipe 最多每 D（例如 50 ms）flush 一次，或窗口照速率乘以往返決定，讓 pump 早一點被擋住。這在 pipes 時沒有選（見[架構](architecture.zh-TW.md#transport)），因為快速鏈路上緊跟在 flush 之後的訊息也要等到 D；留在這裡，給慢速鏈路。

## 同一個檔案系統時，由 kernel 複製

兩個根在這台機器的同一個檔案系統上時，可以讓 kernel 複製檔案，或共用它的區塊，如 `copy_file_range` 與 reflink，而不是由 Ferry 讀了再寫。要檢查複本的什麼、預設開不開，還要決定；當時的建議是不開。沒有量。

## 寫 manifest 的執行緒每一批都等 owner

Source 寫 manifest 的執行緒每一批都問 owner 能不能送，等它回答，是兩條執行緒之間的一趟往返；一個目錄不論空不空就是一批。一個目錄裡 100 萬個空的子目錄的 dry run，它等了 21 秒裡的 13.5 秒，owner 九成的時間閒著；見[掃描](pipeline.zh-TW.md#1-掃描)。
